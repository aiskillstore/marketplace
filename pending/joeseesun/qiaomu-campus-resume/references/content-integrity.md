# 真实性与证据

## 允许的证据类型

每条经历 bullet 使用以下一种：

- `source_resume`：原简历中明确存在；仍需检查明显矛盾。
- `user_confirmed`：学生在当前访谈中明确确认。
- `repository_verified`：从学生授权范围内的仓库、提交或 README 核实。
- `document_verified`：从成绩单、证书、项目文档或正式材料核实。
- `conservative_estimate`：基于用户提供的上下界保守估算，并由本人确认。

禁止 `unknown`、`inferred`、`model_generated`。`source_note` 只用于私下复核，不渲染到 HTML/PDF，也不要包含身份证号、账号密钥或无关个人信息。

## 数字规则

- 数字不是必需品；“完成并上线”“通过验收”“覆盖 6 个核心流程”都可以是有效结果。
- `conservative_estimate` 的正文必须出现“约”“~”“≈”或明确区间，并记录估算依据。
- 不把代码行数当默认质量指标；只有在能解释意义时使用。
- 不把团队整体成果全部归到个人名下；使用“参与”“负责其中”“与 X 人协作”说明边界。
- 不根据技术栈自动推导规模、性能、安全性或商业价值。

## 表达强度

按证据强度选择动词：

- 独立负责且有交付：设计、实现、重构、部署、定位、交付。
- 共同完成：协作完成、参与设计、负责其中的 X 模块。
- 学习/课程实践：完成、复现、搭建、验证；不要写“主导企业级架构”。

## 必须阻断的情况

- 关键时间、组织、岗位或项目归属互相矛盾。
- 为匹配 JD 写入学生没有使用过的技术。
- 量化结果无来源或学生拒绝确认。
- 链接无法对应本人项目，或涉及私密仓库而用户未授权。
- PDF 中出现占位符、模板姓名、示例联系方式或“待补充”。

## 可降级的情况

- 没有 JD：生成岗位族通用版，不能报告“匹配率”。
- 没有量化结果：写范围、复杂度、约束、交付或学习成果。
- 项目较弱：保留 1–2 个最能解释的项目，同时给出未来补强建议，但不在简历里写计划。
- 信息不足：交付草稿 JSON/HTML，PDF 标记为未通过，不伪装成最终版。
