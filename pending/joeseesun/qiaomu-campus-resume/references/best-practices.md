# 简历写作与版式最佳实践

本页是生成、改写和审校简历时的依据。它把权威职业中心、技术院校和招聘系统的共识转成可执行规则；不承诺 ATS 分数、面试率或录用结果。资料检索于 2026-08-05。

## 1. 先证明匹配，再追求完整

- 先从 JD 提取硬门槛、核心职责、技术/工具、业务语境和加分项，再建立“要求 → 事实证据”映射。
- 只保留能帮助目标读者判断胜任力的内容；同一份基础事实应针对岗位调整排序、标题和 bullet，而不是复制一份通投。
- 章节按相关性排序，章节内有日期的条目使用反向时间顺序。大学生通常一页；只有真实且相关的内容无法在清晰字号下容纳时才使用两页。
- 技能区只列技术、程序、语言、实验或工具类硬技能；沟通、领导、协作、批判性思考应在经历中用行为证据展示。

依据：[MIT 本科生简历指南](https://capd.mit.edu/blog/2023/09/01/enhance-your-resume-a-guide-for-first-year-undergraduates/)、[Berkeley 简历指南](https://www.career.berkeley.edu/prepare-for-success/resumes/)、[NACE 技能型招聘研究](https://www.naceweb.org/job-market/trends-and-predictions/what-students-need-to-know-about-the-skills-based-hiring-process)。

## 2. Bullet 使用 A-C-R-E 证据结构

每条 bullet 优先覆盖以下四个槽位，不要求机械按同一语序：

1. **Action**：本人采取的具体动作，以强动词开头。
2. **Context**：解决的对象、问题、范围、约束或团队边界。
3. **Result**：交付、验收、上线、测试、覆盖、采用、变化或可解释的学习成果。
4. **Evidence**：结果来源；只存入私有事实账本，不在公开简历中显示。

可用写法：`动作 + 对象/问题 + 方法/技术 + 结果/验证`。Google 的 X-Y-Z、MIT 的 PAR、Yale 与 CMU 的 Action-Context-Result 本质相同：结果可以是可信数字，也可以是上线、通过验收、合并、部署、完成测试、覆盖场景或交付文档。

硬规则：

- 团队项目必须写清本人负责的模块或决策，不能把团队总成果全部归到个人。
- 没有可靠数字时写范围、复杂度、约束和交付，不制造百分比。
- 一条只讲一个主成果，通常 1–2 行；每项经历优先 2–4 条，弱项 1 条即可。
- 过去经历使用过去式，当前经历使用现在式；中文也要保持动词时态与完成状态一致。
- 避免以“负责、参与、协助、熟悉、了解、学习”停在职责层；若必须使用，后面要立即说明具体动作与结果。

依据：[Yale 高影响力 Bullet](https://ocs.yale.edu/resources/writing-impactful-resume-bullets/)、[Yale 格式与常见错误](https://ocs.yale.edu/resources/resume-formatting/)、[MIT 技能写作](https://capd.mit.edu/resources/resumes-writing-about-your-skills/)、[CMU-SV 技术简历](https://sv.cmu.edu/current-students/career-services/jobs-and-internships/create-your-resume.html)、[Google 简历写作建议](https://services.google.com/fh/files/misc/resume-writing-tips-for-veterans-2021.pdf)。

## 3. 技术学生要展示工程证据

- 项目名称之后先让读者知道项目解决什么问题、本人角色是什么，再展示技术栈。
- 优先写技术决策与工程完成度：数据模型、接口、并发、一致性、缓存、错误处理、测试、部署、监控、性能验证或安全边界。
- 课程项目、研究、竞赛、个人项目和开源贡献都可作为经验；团队项目必须区分个人与共同完成部分。
- GitHub、演示或作品链接只有在可公开、确实属于本人且能支持简历陈述时才保留。
- 技能必须能在项目、经历、课程或证据账本中找到使用场景；不要把 JD 中出现但本人没用过的词塞进技能区。

依据：[CMU 计算机学院简历指南](https://www.cmu.edu/career/documents/resources-by-college/scs-resume-guide-2020.pdf)、[CMU Resume Essentials](https://www.cmu.edu/career/documents/quick-tips/resume.pdf)、[Berkeley 技术简历样例说明](https://www.career.berkeley.edu/prepare-for-success/resumes/sample-resumes/)。

## 4. ATS 安全不等于丑

- 使用单栏、正常文本流、标准章节名和一致的组织名/角色/日期结构。
- 姓名与联系方式放在正文，不放页眉、页脚或文本框；禁止图片型 PDF、表格布局、侧栏、图形、照片、技能条和复杂装饰。
- 输出文本型 PDF，并检查 A4、未加密、字体嵌入和 `pdftotext` 的阅读顺序；岗位系统明确要求 DOCX 时应另行提供 DOCX，而不是宣称 PDF 适合所有 ATS。
- 关键词来自真实事实并自然出现在标题、技能或经历中；关键词重复次数不是质量指标。

依据：[Greenhouse 解析失败原因](https://support.greenhouse.io/hc/en-us/articles/200989175-Unsuccessful-resume-parse)、[MIT ATS 建议](https://capd.mit.edu/blog/2023/09/01/enhance-your-resume-a-guide-for-first-year-undergraduates/)、[Berkeley ATS 格式建议](https://www.career.berkeley.edu/prepare-for-success/resumes/)。

## 5. 视觉系统与自适应密度服务于快速扫描

- 建立三秒扫描路径：姓名/目标岗位 → 最近或最相关证据 → 关键技术/结果。
- 使用 1–2 个字体家族、4–5 个稳定字号角色和一种强调色；同类信息的位置、日期格式、字重和间距必须一致。
- 组内间距小于组间间距；用留白、字重、对齐和细横线建立层级，不依赖卡片和装饰。
- 普通内容优先使用 9.6–10.2pt 正文；只有内容审减后仍很密集才允许降到 9.1pt。页面稀疏时应增大字号和垂直节奏，不用无关经历填满。
- 视觉检查不只看“是否溢出”，还要检查信息是否均匀分布、底部是否因模板压缩造成异常空白、首屏是否能快速找到岗位和最强证据。

依据：[Penn 简历格式指南](https://careerservices.upenn.edu/channels/resume/)、[Penn SEAS 排版建议](https://careerservices.upenn.edu/a-few-resume-application-tips-from-jamie-grant-senior-associate-director-for-seas/)、[UIUC 简历格式指南](https://careercenter.illinois.edu/howtoresume)。

## 6. 生成前审校门禁

逐项检查：

1. 目标岗位的前三项要求是否都有事实证据；没有就诚实标记缺口。
2. 最强两项经历是否都说清个人贡献、关键行动、结果和证据。
3. 每个技能是否至少有一个使用场景；孤立技能删除或降级。
4. 是否存在职责堆砌、同义重复、无法解释的形容词或无来源数字。
5. 是否按相关性排序，并把最强信息放在页面上半部。
6. HTML/PDF 的文本顺序、字体、页数和逐页视觉检查是否全部通过。

中国校招语境同样强调针对性、语言凝练、突出个人作用、STAR/PAR 和结果量化，可参考[清华大学简历工作坊总结](https://career.tsinghua.edu.cn/info/1051/3653.htm)与[清华 IT 组职业教练活动](https://career.tsinghua.edu.cn/info/1012/2703.htm)。
