# 内容与岗位策略

先读取 [简历写作与版式最佳实践](best-practices.md)。本页只保留生成时需要执行的决策规则。

## 总原则

招聘者首先寻找“岗位要求、事实证据、个人贡献、结果”的对应关系。先建立 `JD 要求 → 事实证据 → 简历位置` 映射，再决定保留、排序和改写；没有事实支持的关键词不得进入简历。

## 默认章节顺序

大学生/应届生通用：

1. 姓名、目标岗位、联系方式与链接
2. 教育经历
3. 实习/实践经历（如有）
4. 项目经历
5. 专业技能
6. 奖项/证书/开源（只在有区分度时）

当实习很强时可把经历放在教育之前；当无实习但项目强时，项目紧随教育。自我评价默认删除，除非能用 2–3 条具体证据替代空泛形容词。

## Bullet 结构与评分

优先使用 A-C-R-E：`动作 + 对象/范围/问题 + 方法/技术 + 可证结果`，证据来源保留在私有账本。一条只表达一个主成果，1–2 行为宜。

逐条检查：

- A：是否以本人采取的明确动作开头；
- C：是否说明对象、问题、范围、约束或团队边界；
- R：是否有交付、验收、测试、覆盖、采用、变化或学习成果；
- E：是否存在允许的 `evidence_type` 与可复核来源。

每条必须有 A+C；最强经历至少一条覆盖 A+C+R+E。不要为了凑齐四个字母把一句话写成三行。

可用结果类型：

- 交付：上线、验收、合并、部署、演示、获奖。
- 范围：模块、流程、数据、用户、设备、团队或活动规模。
- 变化：性能、耗时、缺陷、覆盖、准确率、成本的前后对比。
- 技术：关键决策、约束、权衡、测试与定位过程。

避免：负责、协助、熟悉、精通、学习能力强、较好完成，以及没有上下文的关键词罗列。诚实的“参与/协作”可以保留，但必须紧跟本人完成的动作和结果。

## 计算机与技术岗位分支

- 前端：用户流程、组件/状态管理、性能、可访问性、跨端兼容、测试。
- 后端：数据模型、接口、并发、一致性、缓存、消息、可观测性、测试。
- AI/数据：数据来源与规模、基线、指标、验证集、误差分析、部署/推理约束。
- 移动端：平台版本、架构、网络/存储、性能、发布与崩溃治理。
- DevOps/SRE：环境、自动化、部署频率、可观测性、故障恢复、安全边界。
- 产品/非技术：用户问题、调研、流程、协作、交付、指标；不要硬塞技术术语。

技能区按类别列可面试解释的硬技能。熟练程度条、星级、自评分全部删除。云平台应尽量写具体服务；工具只有在项目/经历中能找到使用证据时才保留。

## JD 定制

将 JD 拆为：硬门槛、核心职责、技术/工具、业务语境、加分项。按优先级建立最多 12 项的要求—证据矩阵：`requirement / priority / evidence_ids / status / resume_section`。只把已经存在于事实库中的词自然放入摘要、技能和经历；不做关键词堆砌，也不报告虚构的“80% ATS 通过率”。

若存在硬门槛缺口，简历保持诚实，并在交付说明中指出；不要用近义词伪装具备该能力。

## 内容密度与视觉

- 中文：简洁直接，日期统一 `YYYY.MM–YYYY.MM`。
- 英文：使用自然英文职位/学位名称，禁止逐字机翻；日期统一 `MMM YYYY – MMM YYYY`。
- 视觉从 [六主题系统](style-system.md) 中选择，默认只生成最匹配岗位的一套；用户点名 ResumeCollection 时才从 [简洁参考目录](resume-collection-catalog.md) 选择 `rc-*` 预设。不允许脱离主题令牌随意拼色。
- 渲染器按内容量选择 `sparse / balanced / dense` 密度。稀疏简历增大字号和垂直节奏；高密简历先删弱内容，再压缩间距，正文不得低于 9.1pt。
- 页头和章节标题可使用横向分割线；其余层级依赖字号、字重、对齐、色彩和间距。禁止圆角框、闭合轮廓、侧边栏和彩色侧边线。
- 中文 PDF 按主题实际嵌入 Songti SC、PingFang SC、Menlo 或 TsangerJinKai02；Kami 主题必须使用本机已授权的 TsangerJinKai02 W04，W05 可用于标题。商业字体不随技能包复制。
- 视觉约束不能改变事实、章节语义或 ATS 可解析性。
