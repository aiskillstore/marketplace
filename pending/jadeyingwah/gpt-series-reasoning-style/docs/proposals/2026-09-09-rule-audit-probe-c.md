# 规则审校提案 / Rule-Audit Proposal — AI 丙探针发现的 9 项条文级缺陷

> **状态**：PROPOSAL（提案，未落规则）。只出提案、不改 SKILL/workflow、不升版（对外仍 1.1.0）、不推送。
> **日期**：2026-09-09
> **来源**：第三条低频高危定向探针（AI 丙）的纯条文推演结果。全部引文已逐字核对仓库原文一致；推演未经真实多 Agent 实测，行为类结论一律标「需实测」。
> **处置纪律**：本提案不直接修改任何规则文件；等 AI 甲（67 条评审）与 AI 乙（A/B 验收）结果回来后一并裁决。

---

## 一、问题本质（先读这个）

三条"裸规则"（低频高危、只有条文无示例）在对抗审校下暴露 9 项条文级缺陷。分三类：

- **贯通性漏洞（2 项，P0）**：规则自己的合法路径可以系统性绕过核心防线——修复上限可被清零、身份互斥只查标签不查行为。
- **定义空洞（4 项，P1）**：规则提到但未定义的产物/判据——"发现账本"无模板、"无效轮"计数两歧、指挥官无证据门、身份不匹配无自检。
- **措辞歧义（3 项，P2）**：同文件或跨文件的条文互相顶——用户指名 vs 能力缺口、宿主注入豁免边界、升降级乒乓。

这些不是"执行态守不守约"的问题，是**条文本身读不出唯一行为**——AI 无论多听话，都会在这些点上产生分歧或找到合规绕过。

## 二、缺陷清单（按严重度）

### P0-1｜R2 修复循环上限可被合法动作清零
- **出处**：[multi-agent-closure-rules.md L49-L53](../../references/multi-agent-closure-rules.md)（DRI 处置路径允许"改派唯一 DRI / 亲自接管"）、[agent-modes.md L110-L112](../../references/agent-modes.md)（Failure Fallback 允许"打回一次后收回主干自己做"）、L266-L273（Fix-Loop Cap 锚定"每任务最多 5 轮"）。
- **问题**：5 轮上限锚定在"任务 ID"上。换任务号、换唯一 DRI、收回主干自做——三条都是条文正面允许的动作，但没有任何一条规定"计数器不得重置"。条文推演：上限可以被合法动作系统性清零，等于后门。
- **修订草案**：计数器锚定为**逻辑交付物**且全形态共享——换 DRI/换形态不重置；"收回主干自己改代码"视为主干接手**剩余轮数**而非新任务；任何接管路径须声明"继承已用轮数"；升级给用户必须发生在计数器耗尽时。
- **需实测**：真实多 Agent 回环中该后门被利用的概率（转为"计数共享"后是否引入新误伤）。

### P0-2｜R1 身份互斥管标签不管行为
- **出处**：[multi-agent-closure-rules.md L29](../../references/multi-agent-closure-rules.md)（"不得通过切换身份接管其他角色职责"）、L14（"从其他角色切回时报告越权状态"）。
- **问题**：禁令动词是"切换身份"——一个 AI 全程声明 executor 却在结尾给出"验收通过"判定（审计员职责），从未切换身份，文本上不在禁令射程。且"切回时自首越权"是让正在越权的智能体自我举报，执行上不可依赖。
- **修订草案**：把互斥从"身份声明字符串"移到"动作 × 权限"——声明身份同时声明该身份本次允许的动作集合（reviewer 只读、auditor 出判定）；跨权限动作必须显式请求角色变更；越权检测不依赖自首，由指挥官的证据核验覆盖。
- **需实测**："标签合规、行为越权"在真实验收环节是否真的被拦住。

### P1-1｜R2 第 5 轮硬中断近闭环 + "发现账本"未定义
- **出处**：[multi-agent-closure-rules.md L266-L273](../../references/multi-agent-closure-rules.md)。
- **问题**：第 5 轮出现"有效但差一项验收"的 90% 修复时，硬上限强制中断真实进展；且要求"附发现账本"，但全库唯一账本是 dispatch-ledger（派发台账），"发现账本"无模板——升级合规性不可核查（空账本也"合规"）。也缺"用户允许续一轮"的中间档。
- **修订草案**：定义「发现账本」字段清单（每轮：改动、原因、未解项、证据指针），与派发台账同级落盘；增加缓冲条款——"接近闭环但缺验收时，允许带账本请求第 6 轮，用户批准后重置计数一次"。

### P1-2｜R2 无效轮计数两歧 + "读没读"结构性不可观测
- **出处**：[multi-agent-closure-rules.md L273](../../references/multi-agent-closure-rules.md)。
- **问题**："只重跑不重读的轮次无效"未定义 (a) 无效轮计不计入 5 轮 (b) 如何验证 (c) 后果。计入则误判烧配额，不计入则可无限刷无效轮。且"读没读"是接收方内部行为，用户转交/直接工具模式下指挥官结构性看不见。
- **修订草案**：把判据从不可观测的"读没读"改为可观测事实——每轮返回必须含「本轮事实变化（文件 diff / 命令输出 / 行号）」+「对照上次的 delta 说明」；无 delta 即无效且计入上限；指挥官只对书面 delta 做存在性检查。

### P1-3｜R1 身份-任务包不一致仅靠用户纠正触发
- **出处**：[multi-agent-closure-rules.md L17](../../references/multi-agent-closure-rules.md)。
- **问题**：唯一触发补救是"用户纠正身份时停止"。转交模式下用户只是搬运工，是最不可能发现身份差异的人——规则是被动的（触发靠用户），且无"声明 vs 任务包对照自检"步骤、无不一致后果（产物是否作废）。
- **修订草案**：声明前必须对照任务包 Recipient identity 字段；不一致时自行输出「身份不匹配：包=X / 声明=Y」并停止，产物标 UNVERIFIED；"用户纠正"降级为兜底触发而非唯一触发。
- **需实测**：不匹配在真实转交中是否无声滑过（尤其无观察方的直接工具模式）。

### P1-4｜R3 指挥官扩展无证据门（与子 Agent 不对称）
- **出处**：子 Agent 有强制能力门（[agent-modes.md L61-L73](../../references/agent-modes.md)），指挥官扩展门槛是该文件 L23-L27（角色身份确认 + 协调通道确认）。
- **问题**："能力缺口"是升级指挥官的触发，但指挥官扩展不核验"能力缺口"声明本身——升级合规 = 门禁里一行自我声明理由；且"能力缺口"无定义边界（缺时间算不算？），"不得为展示能力升级"的核心禁令无证据可核。
- **修订草案**：为指挥官扩展补轻量证据门（对称子 Agent）——声明能力缺口必须附两字段：缺什么能力 / 当前会话有什么反证、目标 AI 身份文件路径；无证据拒绝启动扩展标 UNVERIFIED 并回退主干。
- **需实测**：执行态是否真拦截（纯条文无法证明 AI 会如实自查）。

### P2-1｜R3 用户指名 vs 能力缺口冲突
- **出处**：[agent-modes.md L16](../../references/agent-modes.md)（"用户指名的形态永远优先"）vs L25（能力缺口触发指挥官扩展）；例外条款（L38 能力门失败回退）只挂在子 Agent 名下。
- **问题**：两节条文正面冲突——用户指名单 Agent 但任务需要真实浏览器而会话无此工具时，裁决链要翻到另一个文件的授权顺序章，不知道的 AI 随意裁决。
- **修订草案**：在模式自选章内显式写裁决链："任务事实缺口 vs 用户指名冲突时，按授权顺序第 1 条执行；仅子 Agent 能力门失败可回退并标 UNVERIFIED，其余缺口以一句『缺口仍存在，我已回退』上报"。

### P2-2｜R1 "宿主自动注入即可免声明"语义未定义
- **出处**：[multi-agent-closure-rules.md L18](../../references/multi-agent-closure-rules.md)（"宿主已自动注入身份时，可省略重复声明"）与 L24（"角色与承载模型解耦"）并读。
- **问题**：宿主注入的通常是模型/会话名，不是"角色 + 任务 ID"；条文同一词 "identity" 混指两者，给"以模型名冒充角色豁免"留口子。
- **修订草案**：明确豁免边界——只有宿主注入"角色 + 任务 ID"才可免声明；仅注入模型名/会话名不构成豁免；不同宿主的注入内容按宿主实测登记。

### P2-3｜R3 升降级乒乓可绕过"升级需理由"
- **出处**：[agent-modes.md L40](../../references/agent-modes.md)（"形态升级需要任务理由，降级不需要"）。
- **问题**：非对称规则可被"升级(理由A)→降级(无理由合法)→升级(理由B)"切开；任务无形态变更次数上限、无切换账本（对比：派发有台账，形态切换没有）。
- **修订草案**：加"单任务形态变更账本"（复用派发台账或模式三计划）；指挥官扩展在同一任务内累计启用第 2 次起须附累计理由并请用户确认；升级加冷却（上次降级后禁止立即再升）。

## 三、处置边界（尊重现有纪律）

1. **本提案不直接改任何规则文件**——SKILL.md / workflow / agent-modes / closure-rules 一律不动。
2. **7 项为条文级可证缺陷**（P0×2 + P1×4 + P2 中不涉实测的项）：改不改变行为判定，需等 AI 甲（67 条评审）与 AI 乙（A/B）结果回来后，连同本提案一并裁决。
3. **2 项需真实多 Agent 实测才能定修订方向**：P1-3（不匹配触发率）、P0-2（行为越权拦截率）——条文推演只能证缺陷存在，不能证修复有效。
4. 全程不升版（VERSION 保持 1.1.0）、不推送；裁决后如需落规则，另开条目记录，并遵守"对外固定 1.1.0、内部按史实归档"的版本纪律。
