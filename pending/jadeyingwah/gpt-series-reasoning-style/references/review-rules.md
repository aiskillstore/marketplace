# 审查规则（阶段5专用）

## 规则

严格过这8条；**第9条（完成档位）全类型都要过**。轻任务第1–8条只做标★的3条，第9条仍要做。

1. ★ **真打开看一眼**：产物在真实环境打开、真用一遍，不许只看代码或心算就宣布完成。
   - HTML要在浏览器里渲染，API要用前端调，文档要在阅读器里打开。跑脚本不算真打开。
   - 其他类型：交互/游戏类完整走一轮核心玩法；报告类逐个数字对源；SVG/图片类真渲染并放大看细节。
   - 如果环境不支持真打开：如实标"未验证：浏览器渲染"，并给出用户自验步骤（比如"双击HTML文件打开"）。
2. ★ **未验证标注**：没验过的结论直接标「未验证」，写明哪步没法验，不装成全验过。
   - 交付只说三件：做了什么 / 怎么验的（给可复现命令）/ 哪些没验。
   - **如果有未验证的，必须加醒目标记**——在交付物里用星号（*）或加粗标出，让用户一眼就能看到哪些是没验过的。不许把未验证藏在段落中间。
   - 哪些没验的格式：①XX——原因是XX；②XX——原因是XX。不许只写"部分未验证"。
   - **预期符合性也是"没验"的一种**：形象像不像、手感好不好、符不符合你想象的 X——这些只有用户能验，不得折叠进"风格已确认""方向已确认"，必须单独列进"哪些没验"。
   - **未验证项按用户操作链拆分，禁止集合大项**：不许出现"完整玩法流程""整体功能"这类覆盖多条路径的集合词——交付说明里用户能走出的每条操作路径（例：游戏的种植→攻击→击杀、阳光经济、胜负判定各算一条），验证状态必须单独列。操作链从交付说明里数出来，任务类型再多也漏不了。
   - **每项标注错误后果**：崩溃 / 数据错误 / 功能不可用为高风险——高风险未验项必须置顶说明；"错了只是体验差些"为低风险。
   - **宣布"无法验证"前，先穷尽验证手段**：无头驱动、逻辑层测试、直读内部状态、换验证层都试过仍不行，才能标"无法验证"，并给已尝试手段清单。"没去验"和"验不了"是两回事——能验而没验的，验完再交。
   - **查证与创作要分开标注**：交付说明里区分"查证来的事实（给了来源）"与"我自定的设计（未经确认）"——混在一起，用户就没法验证"符不符合预期"。
3. **交付声明对得上**：你说"做了X功能"，那产物里真的有X吗？交付前最后一次回读自己的交付声明，逐项在产物里找位置。指不到的，要么补做，要么删掉那句改成"未完成+原因"。
4. **失败两次换路**：同一动作连续失败第2次，禁止同法第3次；先判断是否与已验路径等价，等价就改代码审查，别死磕。
5. **全绿不算证据**：测试全过只证明跑过的没错。交付前把要防的那个错误故意做一次，断言会红才算验过。
   - 注意：变异后测试照样全绿，说明变异没生效——要先确认变异真的改了代码。
   - 最小菜谱：每个写入口至少打——空值/超长/非法类型/缺键。
   - 非代码产物（文档/设计/SVG/报告）：把最可能出错的点逐一实查——链接逐个点、数字逐个对源、格式逐项看、效果真渲染，并列出查证记录；查证记录就是这一条的"断言红"。
6. **关键数字重算**：数据/研究类交付的关键数字，用独立方法重算或双源交叉验证，对不上以重算为准，不照抄第一遍的结果。
7. **临时物隔离**：运行时临时文件不进交付目录、收尾清掉；清理只动本任务自己的目录，禁全局杀进程。
8. ★ **防死循环**：同一文件连续读3次无新信息就停；同一动作连续做3次输出相同就换思路，别在原地空转耗token。

9. **完成档位如实（全类型）**
   - 交付首行标明 `完成档位：C1` 或 `C2`（定义见 DISCIPLINE.md）。
   - **C1**：必须附「产品档：未拉满 / 已拉满（用户已确认）」——未拉满时写**一句差在哪**。
   - **C2**：必须附用户确认原话/选项卡结果，或外部 scorecard 结果；**没有这些不得标 C2**。
   - **测试全绿、证据清单齐全、变异红过再绿——只证明没假完成，只支持 C1，单独不能升 C2。**
   - 禁止用「风格已确认」「手感已调好」等主观句冒充 C2；未验证标注规则（第2条）优先。

## 退出条件

审查完成，可以交付、任务结束。满足以下全部：
- 该风险等级对应的所有规则都过了一遍（轻任务：★3条 + 第9条；重任务：全8条 + 第9条）。
- 能说出三件套：做了什么 / 怎么验的（给可复现命令）/ 哪些没验。
- **完成档位已标明（C1/C2），且 C1/C2 证据符合第9条。**
- 没有发现未处理的"这里好像有问题"。
