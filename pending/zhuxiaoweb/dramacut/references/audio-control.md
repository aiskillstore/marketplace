# BGM 与音效控制协议

本协议是海外 TikTok 短剧精剪的声音硬门。它把选曲、混音和验收拆成可记录的判断，避免用“轨道存在”代替“观众听得见并感到剧情变化”。

## 事件矩阵先行

逐场建立 `beat matrix`，至少标出 `hook`、`conflict`、`anxiety`、`decision`、`reveal`、`impact`、`emotional_reaction`、`tail`。每项记录输入时码、画面变化、对白锚点、人物状态和一个主声音动作。写入剪辑计划时使用 `beat_events`，其字段、删后时码映射和统一 `kind` 词表见 [计划格式](plan-schema.md)。

- 主声音动作从 BGM 起拍、换拍、升能、撤拍、对白 duck、动作拟音、情绪提示音和有意留白中选一个。
- 每项写 `sound_action=sfx/original/bgm_change/silence`。SFX 用计划 `sfx[].event_id` 关联 beat；原声写具体接触/字词，撤拍写具体音乐段与区间。非空 `cue` 仍只是计划意图；报告 `realized_sfx_event_count` 才说明存在关联音轨，`verified` 声明也不代替实际试听证据。
- 冲突、焦虑、反转、人物意识到线索和片尾钩子不能全部只靠持续 BGM。每个主 beat 至少要有一次可辨的 BGM 变化、duck、音效或留白。
- 30 至 60 秒集默认至少 3 个独立、可解释、能感知的音效事件。冲突加反转的集数通常需要 4 至 8 个。至少覆盖冲突、人物内心或意识变化、揭晓或片尾中的 3 类。少于默认数量时，在报告中写明素材或剧情依据。
- 动作拟音和情绪提示分开计数。一次动作接触可以有一个主拟音，一次人物意识变化可以有一个情绪提示，不能用同一个低频声泛盖所有节点。

## BGM 选曲硬门

BGM 是小短剧的情绪主层。冲突、焦虑、追问、追击、身份疑点和反转优先使用瞬态清楚、起拍快、能量有坡度的片段。平和、慢起、长铺底、没有动态变化的曲目不能用于高能段。

每个高能场景至少比较 3 个候选片段，再确定曲目和源入点。候选表记录文件哈希、分类、前奏静音、首个有效 attack、BPM 或可测节拍、瞬态密度、RMS、动态范围和能量变化。缺少 BPM 时使用波形、频谱和瞬态密度，不凭文件名判断“紧张”。

高能段优先满足以下条件。

- 前奏静音不超过 0.5 秒，首个有效 attack 不超过 0.8 秒。片尾氛围或明确的蓄力段可以例外，但必须在候选表和报告中写明理由。
- 瞬态密度和动态变化处于本次候选的前列。高能段应能测到明显的能量坡度或至少 4 dB 的段内 RMS 波动。
- 片头钩子、冲突、反转和片尾悬念分别对准起拍、增强、换拍或撤拍。30 至 60 秒集默认拆成 2 至 3 个 BGM 能量区，至少完成一次明显换拍、升能或撤拍。
- 同一首歌可以跨场使用，但必须重选源入点或重新编排，不得把一条平床从头铺到尾。沿用旧曲时说明它仍推动当前节拍，并测得对白段和无对白段的可听度。

## 音量、duck 与可听度

“单薄”“像消音”或“温馨处提示音怪”先比较音色或撤层，不反复升降总音量。具体候选、多击完整选段、BGM 分工和有限反馈继承见 [逐项反馈与有限修正](feedback-refinement.md)。

总混音高峰先定位时码，用 full/without/solo 对照各层实际贡献；优先缩短尾音、调整新选段 conditioning 或让 BGM 局部让位。确需短词/瞬态的人声增益调整，只用明确支持的增益操作并回读、原生渲染验证；不把音乐 duck 当成人声处理，也不修改 source duration 绕过诊断。记录实际窗口、增益和前后峰值；数毫秒关键帧未被原生引擎稳定捕获时，先核坐标，再扩到该短词/瞬态前后的可验证平台。

计划同时记录剪映推子语义和渲染语义。`fader_db` 是剪映相对推子，`target_peak_dbfs` 是渲染前选段峰值经过增益后的绝对峰值，两者不能混用。

- 新 BGM 的 `fader_db` 默认落在 -9 至 -5 dB，优先从 -7 dB 起。`target_peak_dbfs = source_peak_dbfs + fader_db`，再换算为线性 `volume = 10^(fader_db/20)`。若源选段峰值不是 0 dBFS，仍按这个公式计算，不能直接把 -7 填入 `target_peak_dbfs`。
- BGM 在对白段必须可感知，同时保留人声清晰度。对白密集段默认做 3 至 6 dB duck，关键名字、否定词和揭晓句可短暂加深到 6 至 10 dB。duck 的 attack 和 release 用 120 至 300 ms 起步，按实际起收音调整。当前 `music.ducks` 只作用于 baseline 中已存在并列入 `music.segment_ids` 的音乐段。新增 BGM 通过 `sfx` 行加入时，必须用分段、局部 fader 或已扩展的 duck API 实现让位，不能只填写 `music.ducks`。
- 新增动作拟音的 `fader_db` 默认落在 -5 至 -2 dB。短提示音和情绪 stinger 先以混音峰值约 -12 至 -8 dBFS 为起点，强命中或明确反转可到 -8 至 -4 dBFS，随后用对白清晰度和总峰值复核。
- 只看推子、轨道数量或素材名称不算完成。必须在渲染后分别测 BGM 独奏 RMS、对白段 BGM RMS、duck 深度、音效 attack 和混音峰值。至少做一次加入前后 A/B，确认 BGM 和音效在正常播放音量下能被感知。
- `qc --edit-report` 会在 `audio_event_measurements` 中自动测量每个新增音频事件的完整选段及 attack 前后窗口，记录实际混音峰值和 RMS；`--attack-window-ms` 控制 attack 窗口半径，默认 80 ms。这些只是混合输出证据，不能分离目标音效，也不能证明实际 duck 深度、目标事件可感知性或主观 attack 对齐，仍须用分轨、A/B 或实际试听补齐。

## 音效落点

先执行 [音效库与选段](sfx-library.md)，渲染后用 [原生独奏/A-B](audio-audition.md) 验证。内置候选可离线用，不要求用户每轮提供 SFX；外部补库按 `assets/sfx-foley/manifest.json` 的来源/许可格式登记。常用类型与逐事件判据见该参考，禁止依文件名直接确定剧情匹配。

每个音效事件记录 `kind`、`target_us`、`attack_offset_us`、`source_start_us`、`source_duration_us`、源峰值、目标峰值、`fader_db`、purpose、尾音和是否 duck BGM。

- 音效主 attack 对齐画面接触、关键字或表情变化，允许误差通常不超过 80 ms。
- `sfx-library measure` 的 onset、主上升沿候选、全局 peak 是不同量；必须先确认源绝对 attack，`prepare` 取 attack 前约 30 ms 与自然尾音，附带 `selection_evidence`。不得所有文件统一裁前 0.5 秒、统一 attack=100 ms。本次已复现这样的选法会截掉主响声。
- 30–60 秒冲突加反转默认逐场检查 4–8 个独立事件机会，包括动作接触、意识变化、反转、片尾；原声足够或有意留白时记理由，不用每次切镜补声。3 个是例外审查线，不是完成目标；同一事件的两下鼓仍算一个。
- 短击打、敲击、命中和提示音保留约 80 至 250 ms 尾音。情绪 stinger 通常保留 250 至 700 ms。密集长声裁短淡尾，不能压住下一句。
- 关键转折缺少合适库素材时，可以从本次选定 BGM 取一个真实瞬态做短提示音，但要单独建可编辑音效轨并在报告中说明来源。不能把整段 BGM 当作“音效”。

## 跨电脑与提交前检查

- 新 BGM 仍只从本次用户选定目录取。SFX 可以来自用户库、剪映库、包内原创/带明确许可的库或本次核准的外部资产；只有 SFX 扩大来源范围。按真实路径和 SHA-256 缓存，换电脑重新建库，不复用旧机器路径或旧聊天的曲目判断。
- 实际使用的 BGM、音效复制到副本 `Resources/Imported` 或本轮资源子目录，最终 JSON 改为副本内占位路径或副本内绝对路径。`register_media` 现在会在 `commit --register-media` 时把新媒体复制到副本 `Resources/Imported` 并改写引用，但提交前仍要检查哈希和最终路径。
- 提交前扫描最终 JSON，禁止残留 `work/`、`analyze/`、`timeline_audio/`、临时预览目录或其他本轮隔离目录的绝对路径。原有分离对白和背景声恢复为草稿内的 draft-relative placeholder 引用。
- 每个实际使用音频都要能在提交后的副本根目录解析并通过哈希校验。`commit/verify` 后用 `readback` 导出最终 JSON 并重绑报告，再从副本实际素材补齐 BGM/SFX 哈希。最终渲染必须使用回读 JSON 和重绑报告再做一次，不拿隔离目录的预览冒充最终副本证据。

## 报告最低字段

每集报告记录 `planned_event_count`、`covered_event_count`、`sfx_count`、`bgm_zone_count`、每段 BGM 的文件哈希、源入点、`fader_db`、能量理由、duck 深度、音效 attack 和最终混音峰值。`apply` 自动产出这些计数、`bgm_zones` 和 `music_ducks`；能量区按删后实际保留的独立音乐段计数，原段理由来自 `music.energy_reasons`，新增段理由来自 `purpose`。`planned_depth_db` 只是计划 duck 深度，实测值必须另记，不能混用。占位路径无法由隔离编辑器解析时哈希为 `null`，应在最终副本回读阶段补齐。没有试听能力时明确写出只完成了波形、峰值和画面核验，不能把有限核验写成“已听感通过”。
