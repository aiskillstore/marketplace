# `/dbs` 组合契约

动态拆解得到多个步骤，或同一步有多个候选时读取本文件。每一步分别回答三个问题：步骤之间怎样流转（流程结构）、多份结果怎样合到一起（合并方式）、哪里需要放行或重新拆分（控制方式）。不要求用户重新发送组合提示词。

## 一、共同约束

- 聚焦同一个当前目标，可以产生配套文件、多个候选结果或尚有分歧的解释。
- 完整读取入选 Skill 和必要引用，核对输入、证据、权限和停止条件。
- 每个成员都有明确用途：承担一个步骤，或检验一种不同解释。仅仅相关不足以入选。
- 从最简单够用的安排开始，删除重复贡献；没有新信息增量时停止扩展。成员越多，交接和冲突成本越高。
- 不预设跨任务长链，不因组合自行创建代理或扩大权限；本文件明确要求隔离对照时，可以使用宿主支持的子 Agent。

## 二、动态拆解

用户的输入事先无法预知，因此不从固定模板里挑组合，而是每次从最终交付倒推：

1. 写出最终交付，找到「交出」能直接满足它的 Skill；
2. 看它的「接手」状态是否已经具备；不具备时，找「交出」该状态的 Skill，依此向前推，直到接上用户当前状态；
3. 用户已具备的状态对应的步骤跳过；同一 Skill 按上游状态选用对应入口；
4. 交付需要的东西写在某个 Skill 的「不交出」里时，不让它承担这一步。
5. 某个状态只能由用户产出（提供材料、看完报告后自己改稿、做出选择）时，把它写成用户回应点，放在需要它的步骤之前。

拆解结果是一串步骤。每一步再按下文选择结构。前一步的实际交出可能改变后续步骤的必要性，拆解随结果更新，不是一次定死的长链。

## 三、流程结构

| 结构 | 适用条件 | 注意 |
| --- | --- | --- |
| 单项 | 一个 Skill 的一个入口就能完成交付 | 默认选择 |
| 串行 | 后一步要用前一步的交出 | 每次交接都使用第六节的交接包 |
| 并行 | 同一对象上有多个互不依赖、只做分析或探索的步骤 | 最终产物只由一个负责成员写；多个成员同时写同一份成品时改为串行 |
| 循环 | 产出质量要求高，且评价标准能在开始前写清 | 先冻结标准，最多修改两轮；批评不再提出新问题时停止 |

并行能扩大覆盖面，代价是各成员各自做出隐含判断，合并时容易冲突。只有步骤之间确实互不依赖时才并行。

## 四、合并方式

| 方式 | 适用条件 |
| --- | --- |
| 直接传递 | 串行步骤，前一步交出即后一步输入 |
| 合成一份 | 并行成员各看一个侧面，共同回答用户的同一个问题或服务同一个决定；由负责成员合成，标出各部分来源，冲突原样保留并说明依据 |
| 选一个 | 多个成员交出同一种东西，按用户的验收条件选出更合适的一份 |
| 比较 | 多个成员代表不同解释或方法，按第五节隔离对照，允许并列或无胜者 |
| 用户挑 | 方向取决于用户偏好；摊开全部选项及取舍，不替用户选。并行探索的合成结果用于选方向时，合成后按此方式交给用户 |
| 分别交付 | 用户提出了几个独立的问题，或要多项互不依赖的产物，各自交付，不合成；其中一步可能改动共享材料（例如看完报告后改稿）时，把它排在前面 |

合并数量服从用户目标：可以是一篇整稿，也可以是文稿及配套标题等多项产物。成员结论冲突时，显示冲突及证据来源，检查前提；未解决的冲突保留，不用汇总措辞掩盖。

## 五、控制方式

### 闸门

某一步回答“该不该继续”时，把它放在会白做的工作之前。闸门只交出放行、改道或停止及理由。只在不放行就会浪费后续工作的位置设闸门，不在每一步都设。

### 隔离对照

同一问题有多种合理解释或处理方法、比较能减少不确定性，或用户明确要求比较 Skill 时使用。

先写清待区分的假设与比较依据。若一个低成本事实问题就能区分，优先取得事实；仍有必要时，通常从两种方法开始，不自动展开全部候选。

1. 各方法使用相同的原始材料和已确认事实，各自形成产出；不把一种方法的结论作为另一种方法的既定事实。
2. 宿主支持子 Agent 时，每个方法交给一个不继承当前对话的子 Agent，只读取自己负责的 Skill，看不到其他方法的过程和答案。不支持时在当前对话中依次处理，并说明后做的结果可能受先做结果影响，不能称为独立比较。
3. 需要评审时，由未参与作答的子 Agent 先根据用户任务写出并冻结可观察的评价标准，再看匿名、打乱顺序的完整答案；看到答案后不改标准。
4. 对产出比较用户的验收条件；对解释比较事实覆盖、反证和可验证预测。文字说服力、用户觉得像自己、多个方法结论一致，都不足以证明因果或效果。同一模型的多种分析仍可能共享偏差，不声称构成独立证据。
5. 事实足以淘汰某个假设、得到满足要求的结果，或继续比较已无信息增量时停止。缺现实证据时指出需要观察什么，不凭空宣布胜出。

对照中的成员只产出答案，不发送、发布、删除或修改共享文件。对照结果需要继续加工时，再按串行交给后续步骤，保留原有不确定性。

## 六、交接包

串行交接时，下一个成员收到：

- **原始材料位置**：用户提供的材料与约束，原样保留；
- **已确认事实**：用户确认或材料直接支持的内容；
- **上一步交出**：前一成员的实际产出；
- **待验证假设**：方法推断和尚未核实的事项；
- **这一步要交出什么**：对应接手字段中的交出；
- **怎样算合格**：用户的验收条件或本步的停止条件。

辅助成员只完成当前分工必要的深度，保留自身硬门槛。

## 七、停止与调整

以下情况停止相关分支，其他不依赖它的工作可以继续：

- 闸门或前一步的交出推翻后续工作的必要前提；
- 缺失必需证据、工具或授权；
- 成员硬边界冲突，无法在当前目标内调和；
- 继续尝试没有新增信息，或当前目标已满足。

停止时交代当前结果、未完成部分、缺口和恢复条件。新事实或反馈推翻前提时，回到动态拆解重新安排，沿用已有上下文。

## 八、用户交付

执行前按入口规则说明收到什么、怎样安排、为什么这样排，随后在当前对话中工作。最终交付简短保留本轮实际使用的 Skill 名称与分工；仅预读、推荐、计划使用或受阻未执行的成员，不列为已经使用；部分执行按实际贡献描述，不声称完成全流程或启动了未实际启动的独立 Agent。

用户只要推荐时给出选择理由与用途差异。需要导出提示词时，才把目标、材料、事实与假设、成员关系、依赖、验收及授权边界整理成可携带的调用说明。
