# Initialization and maintenance

Read this reference after explicit initialization intent or established post-adoption relevance for context assessment or authorized canonical synchronization.

## Adoption

Initialization requires explicit developer intent. Establish the repository root and reuse current project evidence. For a new foundation, confirm adoption is absent; for continuing or completing onboarding, preserve the established foundation and registrations and resume the unfinished scope. When onboarding is already complete and nothing is pending, report the existing setup without rewriting it. Replacing valid adoption requires explicit replacement intent. Canonical adoption requires bounded regular `/moldea/moldea.yaml` and `/moldea/project.md` files, independently of README and AGENTS.md. Their presence does not establish complete structural validity. Managed document drift is a separate setup concern. Partial artifacts do not authorize automatic repair. Explicit project repair follows `project-repair.md` and requires evidence of prior initialization; it does not enter this initialization procedure.

Do not recommend initialization during unrelated work. Do not treat generic knowledge, ordinary documentation, or a repository name as adoption intent.

Create the smallest foundation that accurately represents established current truth. Zero agents, relationships, runtimes, and requirements are valid. Never create placeholder agents or speculative bindings to make a project appear complete. Initialization also onboards evidenced existing agents and cohesive inline model workflows through the agent-design procedure below; it does not invent new responsibilities.

For initialization, reuse the entrypoint's `tooling-installation.md` preflight. An executable-installation hazard preempts foundation classification: follow that reference's complete blocked-install result and stop before invoking the package manager, asking for project purpose, or writing adoption artifacts. Preserve repository controls. Do not repeat completed metadata checks. This preflight does not apply to ordinary canonical maintenance when no tooling installation is required.

## Decide whether foundation evidence is sufficient

Before installing or changing a dependency, creating canonical state, or adding the managed README block, inspect the smallest high-information project-owned sources and classify the foundation:

- **Insufficient:** reliable evidence does not establish what the project does and who or what it serves. Say explicitly that the project is not adopted or was not initialized because the complete adoption contract is absent or the evidence cannot support a truthful foundation; an indirect status such as paused or incomplete is not the adoption result. Identify the exact evidence inspected, state that the sources do not establish what the project is for, and ask one focused question: what does the project do, and who or what does it serve? Do not add generic product-benefit boilerplate to this concise blocked result.
- **Partial:** evidence supports some useful foundation but leaves one material purpose, user, goal, authority, safety, value-bearing, or operating boundary unresolved, or supports consequential conflicting interpretations. Preserve every existing artifact. Name the present and missing canonical foundation elements among `/moldea/moldea.yaml` and `/moldea/project.md`; report document integration separately. Summarize the supported truth separately from the highest-value unresolved boundary, and ask one focused clarification that distinguishes the material alternatives.
- **Sufficient:** evidence establishes a useful project purpose and served people or systems, and no unresolved material boundary would make the persisted foundation misleading. Proceed without a ceremonial question.

Insufficient and partial foundations stop before every dependency, `/moldea/**`, and managed README write. Do not store developer-answerable ambiguity as an unresolved requirement. A repository name, generic label, brief package metadata, placeholder source, or empty export does not establish a foundation by itself. A concise authoritative source can be sufficient when it establishes the necessary truth. Developer-provided context in the initialization request may contribute when its intended authority is clear.

Do not use successful structural validation to justify placeholder truth. Validation proves that files satisfy the repository format; it does not prove that their claims are meaningful or evidence-backed.

A sufficient foundation permits the complete initialization flow below. Do not finish after writing the foundation when existing-agent onboarding remains pending. Initialization does not authorize inventing a new agent or responsibility.

## Establish required tooling before foundation writes

After the foundation is sufficient, reuse the early bounded package-metadata finding. If it establishes a missing compatible local CLI, apply `tooling-installation.md` and complete its authorized safe installation before creating canonical files or the managed README block. Never invoke `validate` or `composition` merely to rediscover known absence. Keep the executable-configuration stop contract and disabled lifecycle scripts; do not bypass installation controls.

An installation failure stops before foundation writes and validation. Preserve existing project files, report any package-manager changes and the exact blocker, and do not claim adoption or automatically roll back dependency changes. A reported installation success does not authorize ignoring known missing or incompatible package metadata. If compatible tooling was already present, do not reinstall it or add an availability probe. The final launcher call still owns executable-provenance verification.

## Write and validate the complete foundation

Keep `project.md` as a concise project entry point: explain the project's purpose, users, goals, and material boundaries, then provide descriptive links that help readers select relevant focused context. Keep detailed rules with their authoritative owners. Link existing architecture, policy, and active decision documents where they already live; never copy those documents into `/moldea/**` or create parallel canonical owners for them. Make focused context reachable directly or through linked topic indexes. When authorized work adds, moves, removes, or changes an owner's responsibility, update the affected navigation in the same change, using known paths and metadata without reading unrelated context. Around 32 KiB for this entry point and 128 KiB for a focused context document are review points for readability and cohesion, never validity requirements, errors, warnings, or automatic splitting rules. A larger cohesive document can remain intact. Keep ordinary maintenance local; broader reorganization still requires explicit intent. Do not run size-measurement commands or audits solely for these guidelines.

When repository evidence establishes no manifest relationship, the complete manifest is exactly:

```yaml
version: 1
```

The file ends with one LF. Do not add a project name, schema field, metadata, empty optional mappings, a `/moldea/project.md` registration, source globs, or any other relationship merely to describe the project or make the manifest look complete.

When inspected implementation evidence establishes that a specific path materially governs a canonical foundation fact, record a narrow `affectedBy` relationship during this already-authorized initialization. Prefer exact paths or established subsystem boundaries. Do not infer a binding from a README link, project name, or nearby source, add a catch-all glob, or backfill unrelated context. Zero relationships and agents remain valid.

Do not validate a partial foundation. Write `/moldea/moldea.yaml` and `/moldea/project.md`, then invoke only the bundled writer with `node <installed-skill-root>/scripts/managed-readme.mjs --repository <absolute-repository-root>`. It owns the exact managed text, validates the root README, creates or normalizes one safe region atomically, and preserves every byte outside that region. Never reproduce the block manually or use another README-writing path. A malformed, linked, invalid, non-regular, or over-limit README stops initialization without validation. After the canonical foundation and explanatory README are written, establish or hand off AGENTS.md integration and smoke-test its command under `project-repair.md` → “Check setup integration”. Complete the existing-project onboarding step below before final validation. Then use the installed skill's closed launcher for final `validate` to confirm the complete initialization, including integration. When it reports a Claude Code integration warning, apply the same section, then validate once more. Report any remaining integration warning with its repair path and, where “Warnings and acceptance” permits, the developer-acceptance path; never silently fix or accept it. On success, stop without `inspect` or another moldea command. The writer is a bounded local skill operation, not a moldea CLI call. On structural failure, follow the entrypoint's supported recovery rule within the authorized initialization scope: establish the complete correction from bounded diagnostics and necessary contract evidence, repair, and validate the resulting state. When the launcher succeeds, do not enumerate dependencies, inspect CLI internals, resolve executable links, search global installations, use transient tooling, or probe package-manager configuration. An unexpected unavailable or invalid tooling result selects `local-tooling.md` only when the authorized operation can establish it. Report the incomplete state if recovery cannot finish; never discard existing foundation files to hide a failed operation.

## Complete existing-project onboarding

Use the `largeTraversal` profile in `local-tooling.md` for initialization, including its existing command, token, and output limits; do not raise or reset them. This selects larger traversal limits, not the repair workflow or its authority.

After writing the foundation and integration, invoke `node <installed-skill-root>/scripts/initialization-inspection.mjs --repository <absolute-repository-root>` once for a bounded metadata inventory. The helper identifies its own distribution as installed, never project-owned. Other Skill paths are ownership-unverified candidates: establish their authoritative source from project evidence before listing them as project-owned. Canonical agent directories are not proof of registration or the absence of inline workflows. Retain the packet; do not repeat unchanged inventory traversal. A `partial` result does not prove absence or complete inspection; an error establishes no inspection evidence. Follow known project indexes or bounded targeted tools and report any remaining discovery limit honestly.

Use project indexes and bounded source inspection to list the existing agents, cohesive inline model workflows, architecture and policy documents, active decision records, and project-owned Agent Skills found, with their paths. Distinguish a real model responsibility from ordinary code or a tool. Do not count the installed moldea distribution as a project-owned Agent Skill. Keep existing documents and skill artifacts in place and link them from the project entry point where relevant.

After the grounded foundation and integration are written, register the existing agents and inline workflows in this same initialization under `agent-design.md` → “Initialize existing responsibilities”. Before registering agents or making the first change to application code, ask one confirmation listing the agents/workflows that will be connected to canonical instructions. A request already asking to include the agents, such as “Initialize moldea including my agents”, supplies that permission; do not ask again. Host restrictions and unresolved material policy conflicts still apply. While awaiting permission, preserve the foundation, report the inventory and pending registration, and do not claim initialization complete or run its final validation.

If the developer declines inclusion or approves only part of the inventory, finish integration and the single final validation for that approved scope. Report excluded responsibilities as not onboarded by that decision; do not claim every found responsibility was registered.

If there are no existing agents or inline model workflows, retain the minimum foundation path above: no placeholder agent, runtime, empty directory, or speculative binding. Finish its existing integration and final validation sequence.

For an approved batch, preserve existing behavior, complete canonical registration and real instruction consumption for every evidenced responsibility, and run the focused project-native checks required by agent design. Do not run preliminary, foundation-only, or per-agent structural validations; use exactly one initialization-wide final `validate` after the last batch write and native check. Supported structural-diagnostic recovery remains bounded by the entrypoint; never call an unfinished or invalid batch complete.

At a limit or blocker, report the foundation/adoption status separately from initialization completion, the inventory, completed and pending agents, changed paths, outstanding verification, and the next unfinished step. Keep progress in the conversation or host handoff, not an invented canonical requirement or new checkpoint file. Retain the actual developer request or decision; a handoff can reference it but never grants authority. “Continue” resumes this initialization: re-establish current evidence, preserve completed correct work, and finish the pending step instead of starting a scaffold or switching to repair. It does not answer an outstanding permission or policy question.

In every initialization response after the sufficient foundation and integration are written, including a confirmation stop or partial progress at a limit/blocker, list the found agents, inline model workflows, architecture/policy documents, active decision records, and project-owned Agent Skills by name or path. A link to project.md alone does not replace this inventory. Report it together with the foundation and supporting project-owned evidence, registered and pending responsibilities, changed files, focused tests, final validation or why it remains pending, material diagnostics including their absence, and remaining limits. When initialization registers impact relationships, report that they cover only source you inspected and name each registered agent whose input, context-selection or output modules you did not inspect. On completion, report the project as adopted and end with one short, evidence-supported `Next:` action. When no project-specific gap remains, continue normal repository work; add durable context only when a new fact needs an owner, and suggest creating a new agent only for a separate developer goal that needs one.

## Maintain owned truth

Relevance permits bounded assessment, not automatic persistence. Informational handoffs, feedback reviews, and read-only planning remain read-only; retain necessary maintenance obligations in the host's existing plan or handoff. For a current-fact handoff, compare the durable facts with the selected owner and report missing context without saving it; keep transient status out. An unambiguous developer correction to established project truth authorizes the minimal update to its existing canonical owner after adoption and ownership are established. A conflicting raw handoff without correction semantics does not authorize a write. No second request naming moldea or ceremonial confirmation is needed. An explicit read-only constraint still forbids writes. Correction authority does not extend to implementation changes, initialization, repair, new canonical assets, or a broader audit.

A developer can select intended policy without proving that software already implements it. Preserve that distinction, proposals, and unresolved factual conflicts. Apply the existing authority rules instead of guessing. Do not ask whether incidental information should be saved unless the answer is necessary for the requested work.

For an authorized relevant change, use one completion sequence:

1. Retain the host task's authorized outcomes, negative constraints, exact implementation paths and hunks, selected canonical owners, declared mirrors, and affected requirement criteria. Identify owners from direct paths, bounded conversational assessment, or valid `scope` results. For owners whose canonical content this task changes, bind only already-inspected implementation paths that materially govern that content under `relationships.md`. Keep detail-level facts with focused owners; `project.md` contains project-wide facts and links, not every feature’s paths. A read-only plan records likely obligations without authorizing writes.
2. Read only selected owners and relevant implementation or consumers. Carry the selected owners and outstanding obligations through host planning, implementation, and handoff. Newly relevant path batches can add owners; unrelated misses cannot cancel earlier owners. Neither compaction summaries nor handoffs supply fresh evidence or write authority.
3. Compare completed behavior with every still-applicable selected owner and mirror. When a selected owner is an agent, tool, or skill, resolve tools and skills to their agent using the scope result's `agentId`. If the batch's changed hunks touch a bound file or an already-known instruction-loader, schema, or tool path, run `runtime-guidance.md` → “Check one connection” once for that agent. Otherwise compare facts and mirrors without a connection trace. Correct contradicted declarations, requirements, and documentation as the smallest coherent authorized change set. Preserve accurate and unrelated content and developer work. An implementation-only edit is incomplete while an established owner or mirror states the old behavior.
4. Before final validation, align `/moldea/moldea.yaml` only for owners whose canonical content this task changes. When already-inspected source materially governs that changed content and its relationship is missing or wrong, add or correct the narrow relationship under `relationships.md`; a gap note does not complete that maintenance. An owner merely assessed during ordinary code work gets no manifest write, even when an inspected governing source lacks a declaration; at most note that gap in one line. The sole ordinary-code exception is to correct or remove an existing declaration made invalid by a file move or deletion in this task, without adding new relationships. Read-only work reports gaps without writing. Preserve valid declarations. `/moldea/project.md` owns only project-wide facts, and a navigation link alone needs no relationship. Do not scan for candidate paths, invent bindings, broaden globs for future work, or search unselected owners. Zero relationships remain valid. Explicit relationship maintenance, including a requested path relocation, and explicit repair keep their own authorized scope.
5. Compare the final state and diff with every authorized outcome, constraint, and path. Record material unresolved facts under their exact owners with resolution criteria and related paths. Finish required project-native checks, then run the narrowest launcher-backed structural validation after the final canonical or relationship write. Follow the entrypoint's bounded recovery rule for structural defects. Report actual results and limitations; structural validity does not prove semantic alignment.

## Warnings and acceptance

Warnings do not invalidate the project: something is worth a look, and nothing is blocked. For each warning whose `acceptable` flag is `true`, state both paths in one line: fix the cause, or accept the warning in `moldea.yaml` with a reason to silence it. Acceptance provides flexibility; present both paths without pushing either. For the non-acceptable `MOLDEA_ACCEPTANCE_UNMATCHED`, state the correction instead: remove the stale entry.

Accepted warnings live in the tracked `moldea.yaml` and apply to every checkout. Offer acceptance of an `integration` warning only when its subject is a shared instruction file that Git tracks: root `CLAUDE.md`, `.claude/CLAUDE.md`, or a tracked `AGENTS.md`. Establish tracked status with the host's Git. The qualifier of `MOLDEA_INTEGRATION_LINK_UNRESOLVED` is its reason, so an acceptance covers only that reason. For `/CLAUDE.local.md` or an instruction file Git ignores, offer only the fix or the handoff, and explain that accepting it would report `MOLDEA_ACCEPTANCE_UNMATCHED` on every checkout without that file.

The developer chooses. Never accept on the agent’s own initiative, silently, or to make a check pass; never write a reason the developer did not give. When instructed to accept, add `acceptedWarnings` with the exact `code`, `subject`, and `qualifier` reported by `validate` and the developer’s reason, then run `validate` once to confirm it reports as accepted. Remove the entry when the developer asks or after its cause is fixed; `MOLDEA_ACCEPTANCE_UNMATCHED` prompts removal. Acceptance never turns an unchecked connection into a passed coverage record.

## Requirements and removal

Before the first write, compare every affected requirement criterion with the authorized requested outcome and classify it as satisfied, outstanding, or evidence-blocked. A matched implementation change authorizes its necessary requirement-state update. When one criterion becomes satisfied, bind the canonical rewrite with the implementation and rewrite both `description` and `resolution` so neither still claims that condition, while retaining every outstanding or evidence-blocked condition. A direction to leave one condition for later preserves that condition and the requirement, not satisfied wording. Remove the requirement only when every criterion is established and the current operation authorizes the removal. When authorized work changes or removes canonical content, remove superseded declarations and stale relationships made unnecessary by that content change; do not retain compatibility paths without an established supported consumer.

A relationship requires reconsideration, not an automatic edit. If an ordinary code task leaves an assessed owner's canonical content accurate and unchanged, preserve its manifest declarations too, except to correct or remove declarations this task itself made invalid by moving or deleting their files. That exception adds no new relationships. Report no more than one line identifying the owner, preserved behavior or contracts, and unchanged canonical state; an established relationship gap may be noted in that same line without adding it.

Keep one owner for each fact. Link an existing authority instead of copying its policy into another canonical asset. Synchronize a declared mirror from its source; do not create undeclared distributed copies or cross-repository paths.

## README marker ownership

moldea owns only the content strictly between these exact markers:

```markdown
<!-- moldea:start -->
<!-- moldea:end -->
```

The markers themselves establish the boundary. A README edit activates maintenance only when a changed hunk intersects the owned content. Changes elsewhere in README, including nearby design routing or a path-only match, are unrelated and must not load moldea resources or run the CLI.

When initialization or an established project-repair correction is authorized, invoke the bundled writer for the canonical block. The asset embedded in that writer is the sole managed-text authority. The README explains moldea and links to canonical state. Ordinary activation belongs only in the managed AGENTS.md block; neither README nor AGENTS.md content establishes canonical adoption. The intentional blank line after the opening marker separates the ownership marker from the Markdown paragraph. Do not add duplicated project context, tool versions, CLI commands, or other workflow rules to the block.

Never rewrite README outside the markers as part of moldea maintenance. This marker boundary limits moldea-specific maintenance and its writer; it does not restrict a host task's independently authorized documentation changes. The writer rejects malformed, duplicated, or ambiguous marker layouts before writing; report its compact structural error and stop.

After every canonical and mirror write is complete, validate current-schema metadata as the final moldea command. A validation performed before a later repair does not verify the resulting state and cannot support completion. Inspect only the changed canonical owners, and do not run full-project content inspection.
