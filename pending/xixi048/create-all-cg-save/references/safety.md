# 安全与合规红线

改别人的存档是"高风险、低容错"的操作。这份清单在整个流程中都必须遵守。

## 铁律

1. **仅限离线单机游戏**。涉及联机对战、排行榜、在线存档校验、反作弊、多人服务器的游戏，不做。
2. **只处理用户自己合法拥有的游戏副本**。不参与破解序列号、绕过 DRM、传播盗版资源。
3. **动手前先弄清楚要改什么**。不知道某段字节是干什么的，就不要改它。
4. **任何写入前必须备份**，且备份落到独立文件，永不原地覆盖。
5. **先 `--dry-run` 再真写**。预演报告和人脑检查是不可省略的一步。
6. **不确定的时候问用户**，不要替用户猜。

## 不要放进仓库的东西

游戏资源有版权，仓库里只允许保留"方法"，不允许保留"内容"：

- 不要提交游戏安装目录里的任何文件
- 不要提交解压出来的游戏脚本、CG 图片、地图数据
- 不要提交完整的存档文件本身

验证时使用的样本放在本地忽略目录中（本仓库已 gitignore `tests/`），只把结论写进文档。

## 备份与回滚

`apply_plan.py` 在写入前自动创建：

```
<存档名>.allcg-bak-<YYYYMMDD-HHMMSS>
```

并在 plan.json 里回填 `backup_path` 与 `backup_sha256`。回滚时会再次校验备份完整性，
校验不过就拒绝回滚 —— 避免用一个已经损坏的备份雪上加霜。

写入采用**原子写**：先写临时文件再 `os.replace`，防止中途崩溃留下半截存档。

## 交付给用户时必须说明

- 备份文件在哪、怎么回滚
- 修改了哪些字段（开关 ID / 变量 ID / 字节偏移范围）
- 必须进游戏实际验证，不能只看脚本报成功
- 已知风险：无脑全开开关可能破坏剧情分支；某些游戏把失败/结束条件也做成开关

## 操作前自查清单

- [ ] 确认是离线单机游戏，无在线校验
- [ ] 确认目标存档路径是用户自己的，且已退出游戏（避免文件被占用/未刷盘）
- [ ] 已有一份未被修改的备份
- [ ] 已明确"CG 解锁"在该游戏里对应哪些字段
- [ ] `--dry-run` 结果已肉眼复核
- [ ] 已告知用户需要进游戏实测
