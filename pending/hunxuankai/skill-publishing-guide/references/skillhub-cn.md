# 腾讯 SkillHub：skillhub.cn

核验：2026-11-08。介绍机制依据当前官方教程、已登录网页的发布/更新表单、公开只读响应及官网加载的客户端。下文区分官方说明、界面/客户端观察和待核验；未填写、保存、上传或提交，不构成服务端更新实测。此前文件过滤观察保留原日期。不要混用 skillhub.club 或字节/企业 SkillHub。

## 两个入口

当前发布界面有“本地上传”和“从 GitHub 导入”。后者提示：先绑定 GitHub 账号，再扫描公开仓库里的 SKILL.md 并选择条目。它不是已验证的匿名任意 URL 提交接口，也不代表以后每次 push 都自动同步。

- **本地上传**：准备完整单技能文件/ZIP；检查展开后的路径与保留文件。
- **GitHub 导入**：核对实际账号、仓库、条目和版本；从多技能仓库中明确选择本次范围，不只看输入 URL。

准备材料不依赖登录。真正操作后台时复用已有可用会话；若需要登录/绑定，再按当前会话规则请求用户处理。

## 简介与概述分别来自哪里

通用内容分层与验收见 [介绍内容同步](introduction-content.md)。不能把发布包、SKILL.md 的 description、GitHub README、平台简介和概述正文合成一个自动同步字段。

### 当前客户端与公开只读观察

- 网页表单将简介 `summaryZh`、自定义概述 `overviewMd` 和上传文件分别组装。已有概述会另行读入更新表单；编辑器“保存”的处理是把文案交回表单，最终“更新 Skill/提交审核”才进入提交流程。不能把编辑器保存或选取 ZIP 写成平台已经接收新版概述。
- 概述渲染在 `hasOverview` 为真时优先读取独立概述；取得非空正文就展示它，为空或读取失败时回退到文件内容。默认文件选择按根路径、不区分大小写依次查找 SKILL.md、README.md、SKILLS.md，并移除 YAML frontmatter。这里的 README 是平台文件清单中的文件，不是自动绑定 GitHub 仓库根 README 的证据。
- 默认文件正文在选择中文且 `contentZhAvailable` 为真时会请求语言版本；顶部简介优先使用 `summary_zh`，其次使用 `summary`。公开只读响应也可分别观察原文简介、中文简介与 `hasOverview`。这些字段和条件证明客户端如何选内容，不能证明翻译何时、依据哪一版生成。
- “用 SKILL.md 填充”将所读文件正文复制到编辑器，随后可编辑。按一次复制的文案处理，不能当作以后每版都会更新的持续绑定。

以上来自 [官网当日客户端](https://cloudcache.tencent-cloud.com/qcloud/tea/app/skillhub/assets/skill-hub.bb2n2rxv.js?max_age=31536000) 的表单、概述渲染与文件读取代码。它是当前实现观察，不是长期稳定的公共写 API 契约；不依据字段名自造更新接口。

### 仍待核验

- 具体旧页面当时采用默认文件、自定义正文还是语言副本，以及不同观测的实际原因；当前页面内容变化不能反推过去的原因。
- 已有自定义概述在更新时省略字段、留空或清空后，服务端到底保留还是清除；是否可独立修改而不新建版本，不能由客户端的省略值决定。
- 自定义概述与各历史版本的绑定关系，提交、审核和公开展示分别何时生效；官方界面的复审提示不代替本次回执。
- 简介/正文翻译的来源、重建触发和缓存更新机制或刷新时限；没有依据不宣称“GitHub push/新版 ZIP 后自动刷新”或给出等待时长。

## ZIP、文件与字段

当前客户端解压后会去掉文件路径的公共目录前缀，并要求归一化根路径有非空 `SKILL.md`。平铺包或带共同外层目录的包都可能正确归一化；没有依据要求外层目录名必须等于 slug。以本次预览后的清单为准。

2026-11-07 客户端观察到最多 200 个接收文件、合计 10 MiB 解压文件大小，并会跳过部分二进制、图片/媒体、PDF/Office、归档等扩展名。这不是已验证的完整服务端契约。若过滤了必要资源，停止宣称包完整，说明具体缺项并确定适配方案；不悄悄删依赖。

普通网页表单目前要求 slug、显示名、非空版本和根 SKILL.md，分类显示为选填；其他流程的分类要求另查。客户端 slug 检查为 2–128 个小写字母/数字/连字符且不首尾连字符。填写项目真实作者版本；不要假定表单一定读取 `metadata.version`，也不要把客户端“非空”检查泛化成服务端 SemVer 或递增规则。[官方 Agent 发布规范](https://skillhub.cn/ai/release.md) 列出的 CLI frontmatter/SemVer 要求与网页检查分开记录，不能推广为通用 Agent Skills 元数据规则。

选用已有 namespace/slug 作为更新身份。不同 namespace 下可以有同名 slug，不能看到同名条目就自动改名。

## 提交与更新

优先按当前正式网页流程完成。客户端观察到的 `POST /api/v1/community/skills/publish` 使用认证及 FormData；这仅说明当前网页如何工作，不构成长期稳定公共 API 或某个第三方 CLI 的保证。确需自动化时先核验官方支持、当前会话和请求语义。

为实际发布或需要用户手动操作的任务，先交付完整可复制的简介与概述 Markdown，覆盖本次功能变化、系统支持、依赖和真实验证范围，然后按已核实的网页入口处理：

1. 在“我的 Skills”确认既有 namespace/slug，选择对应条目“更新”；首次发布走官网“发布 Skill”的本地上传或 GitHub 导入。等当前表单内容加载后，记录已有描述及概述的默认/自定义模式。
2. 核对本次真实作者版本、选定包/来源及展开后的完整文件清单。更新表单可能预填下一 PATCH；它只是客户端建议，不能为修正文案自动升版或与包内版本混用。
3. 在“描述”核对新版简介全文；若使用抓取建议，确认实际采用的是新版所需文案。不要假定选 ZIP 就覆盖旧描述，也不要用变更说明替代简介或概述。
4. 检查“Skill 概述”。采用自定义正文时，进入“编辑概述”，粘贴已准备的完整 Markdown，预览并核对功能、系统、依赖、验证范围和链接，再“保存”回表单；使用“用 SKILL.md 填充”也要比较复制后的内容。采用默认文件模式时，核对实际文件正文和表单模式；已有自定义内容要清空的真实保存语义仍需核验，不能仅凭空字段保证回退成功。
5. 最后核对表单中的版本、简介、概述模式/全文、分类/图标及适用协议；只有在相应发布授权内才执行“更新 Skill/提交审核”。编辑器保存不等于提交，提交回执不等于公开。新条款或原授权没有覆盖的权利变化需要用户决定；不自动选择源代码许可证。
6. 按下节分别记录审核、版本、包、简介与概述的结果。仅咨询或准备时停在完整材料与已核实步骤，不上传、保存平台内容或提交测试条目。

遇到版本重复、上传超时或校验拒绝，先查该 namespace 下的后台记录和具体错误。不要因为公开搜索找不到就重新创建，也不要自动升版绕过冲突。

## 成功证据

当前客户端包含 pending/security_review/admin_review/platform_review、拒绝和 approved 等状态。保留原始返回，并关联此次版本。

上传返回成功、后台存在条目、待审核/审核通过、公开版本生效及网页介绍更新分别核对。最终至少检查四项：

- 公共详情页/API 的 namespace、slug 与目标作者版本。
- 实际渠道下载包的文件、版本与选定来源/哈希；只看版本号或本地 ZIP 不算下载包验收。
- 公开列表/详情顶部的简介；原文与实际语言字段分别记录。
- 详情页概述的完整正文、来源模式/语言/所选版本，确认新版功能、系统支持、依赖和真实验证范围没有遗漏。

版本已公开、简介已更新、概述仍旧可以同时存在。未知审核状态不能自动写成待审；旧版仍公开且本次待审有实际证据时，同时报告“旧版可见、目标新版待审”。用 [发布记录模板](submission-record.md) 保存各项时间、比较结果与未完成事项，不能以摘要、HTTP 2xx 或新版本号代替概述验收。
