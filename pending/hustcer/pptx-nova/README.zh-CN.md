# pptx-nova 使用指南

`pptx-nova` 可以帮你制作、修改、翻新、翻译和检查 PowerPoint 演示文稿。你只需要用日常语言说明想要什么，
它会尽量交付一份真正可编辑的 `.pptx` 文件，而不是一张张截图。

这份文档写给普通使用者。完成安装后，你不需要了解配置文件或内部流程，即可用自然语言提出需求。

## 安装

将 skill 安装到当前项目：

```bash
npx skills add hustcer/pptx-nova --skill pptx-nova
```

如果需要全局安装，按使用的 Agent 选择命令：

```bash
# Claude Code
npx skills add hustcer/pptx-nova --skill pptx-nova -g -a claude-code -y

# Codex
npx skills add hustcer/pptx-nova --skill pptx-nova -g -a codex -y
```

`-g` 表示用户级全局安装，`-a` 指定 Agent，`-y` 跳过确认提示。这些命令只选择 `pptx-nova`；
普通使用者不需要安装开发者侧的 `deckkit-maker` skill。

skill 安装命令不会安装 `xdoc`。实际生成、编辑、转换 PPTX 和渲染预览，还需要单独安装该运行时，
并确保 Agent 可以通过 `PATH` 找到 `xdoc`。使用 Node.js 22+ 时可以运行：

```bash
npm i -g @s8fy/xdoc@0.20.0
xdoc --version
```

原生安装包、平台要求和运行时验证方法见
[xdoc 安装指南](https://github.com/hustcer/pptx-nova/blob/main/docs/xdoc-installation.md)。
完成配置后，直接用自然语言向 Agent 描述演示文稿需求即可。

## 为什么它不只是普通 PPT 生成器

`pptx-nova` 背后使用 `xdoc`——一个**面向 Agent 的原生文档执行 Runtime，用于原生、
可编辑的 PPTX 工作流**。这个定义中的每个词都有明确含义：原生 PPTX 引擎是它的能力核心，
CLI 是公开分发与集成界面，execution layer 是它在 Agent 与文档之间承担的架构角色，而 Runtime
描述的是完整产品，包括文档解析与转换、结构化修改、渲染、验证、报告、证据产物，以及同一版本化
契约下可选的本地 session daemon。

`xdoc` 本身不是 Agent。Agent 与 `pptx-nova` 负责理解用户意图、规划内容和设计、选择工作流、
审阅证据，并判断结果是否可以发布；`xdoc` 则提供确定性的文档边界，让计划能够被检查、执行，
并由证据验证。两层职责可以概括为：

| 层级                | 主要职责                                                                                        |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| Agent / `pptx-nova` | 理解需求，规划内容与设计，构造最小且安全的修改，审阅证据，并决定交付什么                        |
| `xdoc` Runtime      | 暴露已支持的操作，检查原生对象，解析 selector，验证并执行已声明的修改，渲染结果，输出结构化证据 |

这种分工使工作流比一次性生成器或不透明的 PowerPoint 脚本更强。一次生产级编辑可以遵循明确的
生命周期：

```text
发现能力 → 检查真实 deck → 精确选择对象
  → 构造带类型的计划或补丁 → 在不写文件的情况下 dry-run
  → 应用到单独的候选文件 → 再检查、渲染和比较
  → 保存报告与证据 → 通过审阅后才发布
```

它的强大来自多项相互增强的特性，而非来自任何单个命令：

- **对 Agent 自描述。** 正在运行的二进制会暴露版本化 Schema、操作细节、示例、catalog、
  capability status、报告契约和结构化错误。Agent 可以询问当前安装的 Runtime 实际支持什么，
  而不是猜字段名或依赖可能已经过时的 prompt 知识。
- **原生且可编辑。** 在已支持的对象和工作流范围内，`xdoc` 直接处理真实 PPTX package parts
  和幻灯片对象，使文本、形状、表格、图表及其他受支持元素继续可编辑，而不是把它们压平为截图。
- **先计划，再修改。** 确定性的 selector 和不写文件的 dry-run，让目标歧义、未支持操作、
  预计修改和视觉风险在候选文件交付前就可以被检查。
- **优先保留。** 编辑已有 deck 时继承源演示文稿，并尽可能保留未知或未触及的 package data；
  preserve-only 和 unsupported 区域会被明确报告，而不会被静默宣传成完全可编辑。
- **证据是输出的一部分。** 结构检查、语义检查、渲染预览、源文件与候选文件 diff、操作 trace
  和 sidecar 使一次修改可审阅、可回放，而不是只用“文件已经生成”判断成功。
- **本地、轻量、适合自动化。** 预览渲染、PDF 导出和视觉检查不依赖 PowerPoint、完整 Office
  套件或 headless browser。当前的 `v0.20.0` 原生包会因受支持目标不同而略有差异，单个包
  下载大小约 8.4–10.3 MB（十进制）；普通本地任务不需要独立服务器或常驻后台服务。
  多步骤任务也可以按需使用仅监听本机 loopback 的可选 daemon。

小体积属于特定版本的发布证据，不是永久兼容性承诺；平台支持、渲染后端、字体和精确二进制大小，
都应以所选 release 的实际信息为准。当前公开原生目标覆盖受支持的 Linux、macOS 和 Windows
构建。最终渲染仍取决于所需后端和字体，少见或尚未支持的 PPTX 特性仍需要明确复核。

已核对的发布版为 `0.20.0 (91827673)`。Free 支持单用户本地任务，每任务最多 10 页、
压缩 PPTX 输入合计不超过 5 MiB；PPTX、PDF、PNG 等视觉输出带 `structurify.io` 水印。
Personal 与 Enterprise 可移除套餐级页数、大小限制及新增套餐水印，已有签名水印规则仍适用。
Launch plans 支持本地脚本和每用户 daemon，不包含 CI、共享服务器或 Service/API 部署；
这些环境需要另行适用的授权。公开下载默认适用非商业条款，除非另有许可。
canonical 自动视觉审计需要无水印转换授权；Free 仍可生成带水印预览供审阅。

这些能力组合起来，使 `pptx-nova` 更接近一套可检查、可回放的 PPTX 构建和编辑流程，
而不是把内容渲染成图片后塞进幻灯片。

### 新建 PPT 和编辑已有 PPT 使用不同的工作模型

新建演示文稿和编辑已有演示文稿最终都可能输出一个新的 `.pptx` 文件，但两者并不是同一种操作。
真正的区别不在于是否写出了新文件，而在于以什么作为事实来源，以及现有演示文稿是被重新构建，
还是被继承后修改。

| 对比维度         | 生成式创建                               | 保留式补丁编辑                                     |
| ---------------- | ---------------------------------------- | -------------------------------------------------- |
| 事实来源         | 需求说明、大纲、结构化内容模型或生成代码 | 已有 PPTX，包括其中的页面和原生对象标识            |
| 主要操作         | 根据生成模型组织并写出整份演示文稿       | 检查源 deck、定位已有对象，并应用声明过的修改      |
| 未要求修改的内容 | 按生成模型中描述的内容重新创建           | 默认保留；出现可确认的越界修改时，验证不通过       |
| 输出方式         | 新生成一份演示文稿                       | 默认从源 deck 派生并输出一份单独验证过的候选文件   |
| 验证重点         | 整体内容、设计、版式和渲染质量           | 目标覆盖、定位准确性、格式保持、修改边界和视觉回归 |

对于普通的已有 deck 编辑，`pptx-nova` 使用第二种模型。它会先检查真实 PPTX 结构，找到与用户要求
对应的原始对象，在工作副本上应用结构化补丁，再在发布前比较候选文件与源文件。这是一种
**保留源文件结构的对象级编辑**，而不是先建立一套新的生成模型，再逐页重建整份 deck。

“限定范围”并不等于“只能改很少内容”。声明的范围可以是一段文字、一个图表、几页幻灯片，
也可以是覆盖整份 deck 的主题修改。它表示写入前会明确预期边界；可确认的边界外修改不能被静默交付，
而是必须得到解释、修正或明确批准。

这也不是说 PPTX ZIP 包会按字节直接原地修改。默认情况下，原文件保持只读，结果会写成单独的候选文件。
这里强调的是编辑语义：已有 deck 继续作为事实来源，在支持范围内继承并直接定位其中的原生对象，
同时验证最终修改是否符合声明的范围。

部分请求会有意采用其他路径。把旧 PPT 只当作视觉参考、同时提供全新内容，属于新 deck 生成；
翻新通常属于范围更广的保留式转换，在保留源内容和对象的基础上改变视觉系统。只有当用户明确要求
完整重排、无法安全保留，或用户明确同意相关取舍时，才会进入完整重建路径。

## 高保真 PDF 导出

除了制作和修改 PowerPoint 文件，`pptx-nova` 还可以把已有或刚生成的 PPTX 高保真导出为 PDF，
适合分享、打印、归档、正式交付，以及在没有安装 PowerPoint 的设备上审阅演示文稿。

`xdoc` 会把幻灯片的静态显示效果渲染到 PDF。PDF 不会保留动画、转场、视频播放或其他交互行为；
如果原文件依赖当前环境没有的字体或较少见的 PPTX 特性，导出后仍建议做一次视觉复核。

## 让后续编辑稳定遵守已声明的规则

多数演示文稿工具会把“以后新增页面继续使用这个标题颜色”之类的要求只当作临时聊天上下文。
`pptx-nova` 可以为当前 deck 保存用户明确声明的 future/carryover 规则，并在后续编辑中继续应用。

这项能力依赖可检查的契约，而不是 Agent 临场记忆：

- 明确记录用户原话、适用事件和当前 deck revision。
- 在交付前处理规则冲突、陈旧 deck revision 和用户明确声明的单次覆盖。
- 对当前支持的规则，检查最终 PPTX，确认指定样式确实进入了新增页面或元素。
- 如果规则不适用于当前操作，不会增加额外编辑目标或交付证据。

当前版本刻意保持窄而确定：只支持可以被确定性验证的当前 deck 延续规则，例如保持编辑不变量，
或为新增元素应用指定的标题字体色、总结框填充色。它不会从模糊反馈中推断长期偏好，不会自动建立
跨项目用户画像，也不会允许 session rule 绕过模板约束和质量检查。

例如你可以这样说：

```text
对于这份 deck，后续新增页面都继续使用相同的蓝色标题。
```

## 你可以让它做什么

你可以用 `pptx-nova` 做这些事情：

- 从一句话或一段说明生成一份新的 PPT。
- 根据你给的大纲、Markdown/文本材料、网页或 PDF 提取内容整理成 PPT。
- 参考一份已有 PPT 的风格，做一份内容不同的新 PPT。
- 套用公司模板，把新内容填进去。
- 翻新一份旧 PPT，让它更统一、更专业，但保留原本内容。
- 对已有 PPT 进行保留式补丁编辑，例如改标题、替换数据、调整页面、换图片或改配色，
  而不是为了一处修改逐页重建整份 deck。
- 把 CSV、JSON 或表格数据做成表格页或图表页。
- 翻译已有 PPT，并尽量保持原版式、图表、备注、动画和转场。
- 添加、修改或删除基础动画和转场，例如淡入、逐条出现、自动切页。
- 做品牌改装或品牌检查，例如统一品牌色、字体、logo 和页眉页脚。
- 比较源 PPT 和修改后 PPT，辅助核查改动范围和视觉差异。
- 对普通的已有 deck 编辑使用限定范围的 Edit Contract，让 Agent 在交付前证明请求目标已被覆盖，
  且无关对象没有发生可确认的意外修改。
- 保存当前 deck 中明确的 future/carryover 规则，例如“后续新增页继续使用相同标题颜色”，并在后续编辑中
  验证适用规则是否落实。
- 将已有或生成的 PPTX 高保真导出为 PDF，方便分享、打印、归档、正式交付，或在没有 PowerPoint 的
  环境中审阅。
- 导出图片预览、Markdown、JSON 或文本，方便检查或后续处理。
- 处理含公式的技术页：简单公式可保留为普通文本，复杂公式可作为公式资产插入。
- 检查 PPT 是否有文字重叠、内容被截断、页面不整齐等问题。
- 在你明确要求时，对一次 `pptx-nova` 使用过程给出工作流反馈。

网页、HTML 和 PDF 可以作为内容素材输入。`pptx-nova` 会先把它们提取成 Markdown 或文本，
再进入 PPT 生成流程；它不会默认把网页或 PDF 的原始版式、图片和样式完整搬进 PPT。

## 最简单的用法

你可以直接这样说：

```text
用 pptx-nova 做一份 8 页中文路演 PPT，主题是 AI 质检平台，受众是制造业 CIO，
风格要专业、清爽，输出 ai-roadshow.pptx。
```

也可以这样说：

```text
把 qbr.pptx 翻新一下，内容不要变，视觉更像咨询公司汇报，输出 qbr-new.pptx。
```

或者：

```text
修改 qbr.pptx，把第 3 页的 KPI 数据换成 data.csv 里的数据，不要覆盖原文件。
```

## 你最好提供哪些信息

不需要一次说得很完美，但如果你能提供下面这些信息，结果通常会更好：

- **用途**：这是路演、内部汇报、销售材料、培训课件，还是客户提案？
- **受众**：给老板、客户、投资人、同事、学生，还是公开演讲？
- **页数**：大概几页，或者是否有固定页数。
- **语言**：中文、英文、其他目标语言，还是多语言混合。
- **内容**：大纲、Markdown/文本材料、CSV/JSON 表格数据、粘贴表格、旧 PPT、网页链接、PDF、图片或 logo。
- **风格**：正式、简洁、咨询风、科技感、品牌规范、课程风等。
- **限制**：哪些内容不能改，哪些页面必须保留，是否允许重排结构。
- **输出**：最终文件名，是否需要高保真 PDF 或图片预览。

你可以只给一句话开始；如果信息不够，助手会根据任务情况继续推进，或在关键地方向你确认。

## 常见需求写法

### 1. 快速生成一份新 PPT

```text
用 pptx-nova 快速做一份 6 页中文产品介绍 PPT，主题是企业知识库助手。
受众是销售团队，风格简洁、商务，输出 product-intro.pptx。
```

适合：你有一个主题，但还没有完整大纲。

### 2. 按大纲生成 PPT

```text
根据下面大纲生成一份 10 页 PPT，中文，风格正式，用于季度业务复盘。
1. 封面
2. 本季度业绩概览
3. 收入变化
4. 用户增长
5. 重点项目进展
6. 风险与问题
7. 下季度目标
8. 资源需求
9. 行动计划
10. Q&A
```

适合：你已经知道每页要讲什么。

### 3. 参考已有 PPT 风格

```text
参考 reference.pptx 的视觉风格，用 new-outline.md 的内容生成一份新 PPT。
不要复用 reference.pptx 里的旧文案，只参考风格和页面节奏。
```

适合：你喜欢某份 PPT 的风格，但要做一份新内容。

### 4. 翻新旧 PPT

```text
翻新 old-report.pptx，页数和内容保持不变，整体更专业、更统一。
输出 old-report-refined.pptx，并给我图片预览。
```

适合：旧 PPT 内容还可以，但视觉过时、不统一或不够正式。

### 5. 修改已有 PPT

```text
修改 sales.pptx：
第 2 页标题改成「2026 年销售目标」；
第 5 页替换成 new-chart-data.csv 的数据；
输出 sales-updated.pptx。
```

适合：你希望继续以现有 PPT 为事实来源，同时修改一组明确声明的对象或属性。这个范围可以很小，
也可以覆盖整份 deck；关键是边界明确并且能够被验证。

对于普通的已有 deck 编辑，`pptx-nova` 不只检查 PowerPoint 命令是否执行成功。它会把源演示文稿
默认视为只读文件，检查并定位其中已有的原生对象，在写入前记录允许的编辑范围，再把请求的补丁应用到
工作副本。在发布候选文件前，它还会检查目标覆盖、可确认的意外修改、必要的格式保持和新增视觉回归。

这与生成式重建不同：`pptx-nova` 通常不会因为只需要修改一个标题、图表、图片或样式，就先建立新的
演示文稿模型并逐页重建整份 deck。如果证据不属于当前源文件或候选文件、对象定位存在歧义，或者出现
可确认的范围外修改，交付会被阻止，必须重新检查或生成，而不是静默交付。复杂或暂不支持的 PPTX 对象
以及最终视觉判断，仍可能需要专项检查或人工复核。

### 6. 套公司模板

```text
用 company-template.pptx 的模板和品牌风格，把 outline.md 做成一份新 PPT。
尽量保留模板的版式和占位符。
```

适合：公司有固定模板，不能随便换风格。

### 7. 只做检查或导出

```text
检查 final.pptx 有没有文字重叠、截断或版式问题，不要修改文件。
```

```text
把 final.pptx 高保真导出为 final.pdf，同时生成每页 PNG 预览。
```

适合：你已经有 PPT，需要便于分享、打印或归档的 PDF、质量检查或图片预览。PDF 会保留幻灯片的
静态显示效果；动画、转场、视频播放和其他交互行为仍只存在于 PPTX 中。

### 8. 翻译已有 PPT

```text
把 product-deck.pptx 翻译成英文，尽量保持原版式、图表样式、备注和动画。
输出 product-deck-en.pptx，并给我原文和译文对照预览。
```

适合：你要把一份现有 PPT 翻成另一种语言，并希望视觉结构基本不变。

### 9. 修改动画或转场

```text
修改 launch.pptx：第 4 页的要点按点击逐条出现，第 6 页转场改成淡入。
其他动画不要动，输出 launch-animated.pptx。
```

适合：你只需要基础进入、退出、逐条出现或页面转场。复杂路径动画、视频 timing、
点击某个对象触发等高级效果可能需要先确认能否安全编辑。

### 10. 品牌检查或品牌改装

```text
检查 proposal.pptx 是否符合 brand-profile.json 里的品牌色、字体和 logo 使用要求，不要修改文件。
```

```text
把 proposal.pptx 改成 company-template.pptx 的品牌风格，内容不要变，输出 proposal-branded.pptx。
```

适合：你要统一品牌视觉，或在交付前确认 PPT 是否偏离品牌规范。

### 11. 比较、抽取或给反馈

```text
比较 old.pptx 和 new.pptx，告诉我主要改动和需要人工复核的页面，不要修改文件。
```

```text
把 final.pptx 导出成 Markdown 和 JSON，方便我做内容审查。
```

```text
检查这次 pptx-nova 生成流程有什么使用反馈，并写到反馈文件里。
```

适合：你已经有 PPT，只想做只读核查、内容抽取，或希望把一次使用中的工具/流程问题记录下来。

## 交付时你会得到什么

通常会包含：

- 一份最终 `.pptx` 文件。
- 如果你要求，会有 PDF、图片预览、Markdown、JSON 或文本导出。
- 简短说明：改了什么、生成了什么、有没有需要你注意的地方。
- 如果任务复杂，会保留一份可审计的工作记录，例如 `outline.json`、`deck_lock.json`、
  `content.json`、`patch.json`、检查报告、预览图和 contact sheet，方便后续继续修改或排查问题。
- 如果你明确说“后续新增页面/元素继续遵守某项规则”，还可能保存当前 deck 专用的
  `session-rules.json`。它会记录规则原文、适用事件、冲突和 deck revision，并在后续编辑中通过
  Edit Contract 验证；不会自动变成跨项目的长期偏好。
- 对正式交付、翻新、翻译、模板跟随、图表表格或动画任务，还可能包含更细的验证证据，
  例如 `visual_review.json`、`pptx-diff.json`、`structure-check.json`、`semantic-audit.json`、
  `clean-open.json`、`translation-compare.png`、`translation-compare.json`、
  `refurbish-compare.png` 或 `refurbish-compare.json`。这些文件只在相关任务中出现，
  不会为了凑清单而补造。
- 对翻译或翻新任务，正式交付目录通常还会包含完整的逐 slide 源文件/交付文件对比集合。
  20 页以内保持单图；更大的 deck 使用带编号的多张高 DPI 图片和覆盖 manifest，避免超长画布失败。

默认不会覆盖你的原始 PPT。除非你明确要求“直接覆盖原文件”，否则会输出到一个新文件。

## 哪些材料特别有帮助

如果你有这些材料，可以一起提供：

- 公司 logo、品牌色、字体要求。
- 以前做过且你喜欢的 PPT。
- 公司标准模板。
- 产品截图、架构图、人物照片、客户案例图片。
- 表格数据、图表数据、指标口径说明。
- Markdown/文本大纲、参考文案、官网、白皮书、PDF、会议纪要。
- 翻译术语表、品牌规范、品牌 profile、颜色和字体要求。

如果缺少 logo、截图或官方素材，助手不会假装生成“官方素材”。它会用文字、简单图形或占位说明替代，
并在结果里告诉你。

## 翻新 PPT 时要知道的事

“翻新”通常表示：内容不变，视觉变好。

所以默认会尽量保留：

- 原来的页数。
- 原来的文字和主要观点。
- 表格、图表、图片、备注等可见内容。
- 页面之间的逻辑顺序。

如果旧 PPT 本身内容太密、页面装不下，通常会先尝试保留原生对象并调整版式；确实需要拆页、
合页、重排或删减内容时，必须先让你确认。默认不会把源页整页截图塞进新 PPT 来冒充可编辑翻新。
机器检查通过后，翻新类任务通常仍需要打开 contact sheet、逐页图片和同目录的
`*-refurbish-compare-<MMDDhhmmss>.png`，或完整的
`*-refurbish-compare-<MMDDhhmmss>-01.png`、`-02.png`……编号集合做最终视觉复核。

## 什么时候需要先确认

这些情况通常更适合先确认大纲或方向，再生成完整 PPT：

- 投资人路演、董事会材料、客户正式提案。
- 公司品牌要求很严格。
- 页数很多，或资料很多。
- 你要求“严格套模板”。
- 你要求保留翻译术语、法律措辞、品牌语气或特定表达。
- 你不希望助手自行补充事实或改写观点。
- 旧 PPT 内容很复杂，翻新时可能影响原内容。
- 你要编辑复杂动画、视频播放顺序、SmartArt、宏或其他 PowerPoint 高级对象。

如果你赶时间，也可以直接说明“先快速出一版”，助手会尽量减少来回确认。

## 不适合这样要求

为了保证 PPT 能继续编辑，不建议这样使用：

- “直接把每页截图塞进 PPT 就行。”
- “旧内容可以随便删，只要看起来高级。”
- “参考 PPT 里的图片都拿来用”，但没有授权或来源说明。
- “覆盖原文件”，但没有明确备份或输出路径。
- “严格按模板”，同时又要求完全不同的页面结构。

## 一句话模板

你可以复制下面这个格式来提需求：

```text
用 pptx-nova 做一份【页数】【语言】PPT，主题是【主题】，
受众是【受众】，用途是【用途】，
风格希望【风格】，
内容来自【大纲/Markdown 或文本材料/旧 PPT/CSV 或 JSON 数据/网页或 PDF 提取内容】，
输出文件名是【文件名.pptx】。
```

示例：

```text
用 pptx-nova 做一份 12 页中文 PPT，主题是 2026 年产品路线图，
受众是公司管理层，用途是季度战略会，
风格希望正式、清爽、偏咨询风，
内容来自 roadmap.md 和 metrics.csv，
输出文件名是 product-roadmap-2026.pptx。
```

## 维护者说明

这一节面向维护和发布 `pptx-nova` skill 的开发者。普通使用者不需要阅读。

### 独立运行契约

`pptx-nova` 发布后应能作为独立 skill 运行，不依赖当前开发 monorepo 的根目录文件。

- 脚本从自身位置推导 `<skill-root>`，不要依赖仓库根开发工具、本地环境文件或 agent 私有上下文文件。
- 项目输入通过显式参数传入，例如 `--root`、`--asset-root`、`--xdoc-bin`、PPTX 路径或
  已文档化的环境变量。
- Deck generation path 使用 bundled assets；不要从网络或本机 checkout 动态读取图标、模板或私有素材。
- `xdoc` 是主要的外部文档执行 Runtime，通过其公开 CLI 调用。没有 `xdoc` 时，内容验证、
  DeckKit 选择、icon 查询和 patch build 仍应可跑；真实 apply、convert、vision-check
  会失败或被上层跳过。

### 公开前检查

在公开仓库根目录中优先跑聚合检查：

```bash
nu tools/ci-check.nu
```

它会依次运行公开发布所需的 smoke test、public audit、示例内容校验和 delivery DeckKit readiness 检查。
如果只需要单独检查，也可以分别跑：

```bash
node tools/pptx-nova-smoke-test.mjs
node tools/pptx-nova-audit-public.mjs --strict
```

`tools/pptx-nova-smoke-test.mjs` 只使用 `pptx-nova/` 内 bundled files。它覆盖：
content validation、DeckKit patch build、icon pack query、DeckKit selector、当前 deck session rules
规范化与解析、Edit Contract 源文件绑定，以及候选文件与 evidence hash 绑定。

`tools/pptx-nova-audit-public.mjs` 检查：

- 维护者机器上的绝对路径和私有仓库路径。
- 当前 monorepo 私有上下文泄漏。
- unexpected binary files。
- Tabler icon pack license 是否随包携带。
- examples 是否声明 synthetic / redistributable policy。

`tools/ci-check.nu` 还会校验 `pptx-nova/assets/examples/deckkits/*/content.json`，并对 production/default
DeckKit 运行 `<skill-root>/scripts/cli/deckkits/readiness.mjs --target delivery --benchmark-mode catalog`。

### Tabler 图标包

运行时查询使用 bundled `assets/icons/tabler-icons.pack.br`。在 `pptx-nova/` 目录内刷新图标包时，
必须显式提供 Tabler checkout：

```bash
node scripts/cli/assets/icons.mjs generate --source-root <tabler-icons-checkout>
node scripts/cli/assets/icons.mjs generate --source-root <tabler-icons-checkout> --check
```

也可以设置：

```bash
TABLER_ICONS_ROOT=<tabler-icons-checkout>
```

不要在源码、manifest 或文档中保存维护者机器上的 Tabler checkout 绝对路径。
