## Reading order after entering the project

1. Read this file (AGENTS.md) first.
2. If `cairn/ROADMAP.md` exists, read it for the roadmap, current focus, and open questions (ROADMAP is optional; a minimally-initialized project may not have one).
3. Read the most recent entries in `cairn/LOG.md` (newest entries are at the top) for recent progress and key decisions.
4. Read the relevant `cairn/` topic notes as needed for the task at hand.

## Document responsibilities

| File | Role | Maintenance |
|---|---|---|
| `AGENTS.md` (root) | Rules and navigation | Rarely changes, ≤ 60 lines |
| `CLAUDE.md` (root) | One-line `@AGENTS.md` stub | Written once, never touched again |
| `cairn/ROADMAP.md` | Roadmap and progress | Updated in place, kept concise |
| `cairn/LOG.md` | Chronological log | New entry added at the top (newest first), each entry ≤ 20 lines, summary + pointer only |
| `cairn/<topic>.md` | Knowledge topic note (current truth) | Updated in place; pitfalls go in a body section, tagged via `contains`; revisions get a LOG pointer |
| `cairn/Reference/` | External raw input | Created as needed; append-only |
| `cairn/Cited.md` | Knowledge base citation list | Pointers only, never copies of the source |

> Everything else is created only when a concrete signal calls for it (a decision needs to be recorded, a pitfall gets solved, a goal outlasts one session) — not pre-built as empty shells. Engineering assets (contracts/config/specs consumed by code or process) are not managed by this system; they stay in the code tree, not in `cairn/`.

## Conflict arbitration rules

- Priority: **topic notes > LOG history**; rule-level conflicts are resolved by this file.
- Business/design conclusions follow the latest record in the `cairn/` topic notes, not older LOG entries.

## Knowledge base consumption reflex

- Before work whose reusable kernel — any conclusion it produces or depends on — would be graduation-worthy, check {{KNOWLEDGE_INDEX}} first; add a `cairn/Cited.md` entry only for notes that actually shaped the output (pointers only, never copy the body text).

## Document collaboration rules

- Before making a change, judge whether the user wants "discuss/suggest" or "just edit the doc directly"; when they say "take a look first / evaluate first," give analysis first — don't rewrite a formal doc outright.
- When correcting a past judgment, append a correction note; don't silently overwrite it.
- Don't write an unconfirmed judgment as a settled fact.

## Knowledge distillation rules

- After every substantive step forward, add one entry to the top of `cairn/LOG.md` (summary + pointer); let conclusions settle into the `cairn/` topic notes.
- Cross-project reusable experience gets distilled into {{GRADUATION_TARGET}} via the graduation mechanism.
