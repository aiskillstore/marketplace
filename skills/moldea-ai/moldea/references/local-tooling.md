# Local moldea tooling

Read this reference only after relevance when local CLI proof, machine-contract interpretation, or validation recovery is required. It owns observation, invocation, and diagnostic recovery, not installation. Read-only work never authorizes dependency, lockfile, or configuration changes; report unavailable deterministic evidence. An explicit moldea operation that cannot change tooling reports in one line when the installed CLI is older than `metadata.cliRepairVersion` or lacks a supported root declaration, and suggests an explicit repair; ordinary work stays silent about a compatible CLI older than the repair target. After a relationship hit, a launcher that cannot run the CLI, because of a missing install, an unresolvable layout, or an unsupported Node.js version, is reported in one line with its message and the next step. Explicit repair or another authorized write-capable operation may use `tooling-installation.md` for necessary recovery to the selected skill's `metadata.cliRepairVersion`. Skill updates alone authorize no project change.

For a direct request to prove or safely invoke the local CLI, apply this reference before inspecting a declared dependency, package-manager provider, binary link, or other provider evidence and before reaching any conclusion. The required first proof attempt is the closed launcher `composition --json` call below.

## Supported contract

Skill 10.0.1 supports Git `>=2.32.0`, Node.js `>=22.17.0`, stable `@moldea.ai/core` releases satisfying `^9.0.0`, stable `@moldea.ai/cli` releases satisfying `^13.0.0`, repository format 1, and CLI JSON schema 7. Never substitute a global, transient, out-of-range, or prerelease CLI.

Use only `<installed-skill-root>/scripts/moldea-cli.mjs`. The launcher resolves the repository-root-local package and executable, verifies the package name, exact installed stable version, supported repository declaration, declared `moldea` binary, installed Core against both the CLI's declared range and moldea's supported range, the running Node.js version against the CLI's `engines.node` range, and resolved-path containment from inert package metadata, then invokes the executable without a shell. A missing install or unsupported Node.js version is refused in one sentence. A supported root declaration is a root `devDependencies` entry for `@moldea.ai/cli` that is either the exact installed stable version or a caret range on a stable 13.x version that the installed CLI satisfies; any other range, or an entry outside `devDependencies`, is unsupported. Package management and repository setup or CI own lockfile consistency; the launcher does not read target-project lockfiles. Do not reproduce these probes, inspect links manually, search parent workspaces, inspect unrelated repositories, use package-manager launchers, or search `PATH` for another copy.

Reuse the exact skill root already selected by the host. Package metadata and containment establish a supported local layout, not executable authenticity. The launcher is not an OS sandbox and may execute repository-installed code under the host's existing repository-trust and execution controls. Do not weaken those controls or add a new per-command approval ceremony. The AGENTS.md precheck is separate: it runs the bundled gate before loading SKILL.md and executes no repository dependencies. Repeatable `--path` inputs are relative to the absolute repository root, including from nested directories. Ordinary failures silently return `0`; explicit setup smoke tests use `--diagnose` to distinguish failed execution from a healthy miss. `managed-agents.mjs` owns write and `--print` modes. Core reports integration warnings during `validate` and `inspect`; setup repair and manual handoffs belong to `project-repair.md`.

A declaration, lockfile entry, package name, reported version, Plug'n'Play package location, or package-manager binary shim is not launcher-verifiable installation provenance. The closed launcher supports only the repository-contained package and executable closure it can resolve and validate directly. A Plug'n'Play-only layout without that closure is unavailable; do not guess another provider. A package-manager shim that selects a different provider does not override a launcher-verified package-owned executable, and the package manager must not be invoked to resolve the disagreement.

For every direct request to prove or safely invoke local CLI availability, invoke the installed skill launcher once with `composition --json` after adoption is established. This attempted launcher proof is required even when repository metadata already suggests that the closure is unavailable or a package-manager provider conflicts. Do not stop at package declarations or manually execute a package-manager shim. If the launcher cannot resolve a Plug'n'Play-only package location into its required repository-contained `node_modules` closure, report that the declared compatible dependency exists but the launcher-verifiable package and executable provenance is unavailable in that layout. If the launcher verifies its package-owned executable while supplied Yarn evidence identifies another `node_modules/.bin/moldea` provider, report both facts separately: the conflicting symlink is not authority for the supported launcher path, and neither Yarn nor that provider was invoked. The launcher owns executable provenance; when the direct task explicitly asks to compare an already identified conflicting provider, one inert exact-path symlink-target read may establish that separate Yarn-provider fact without invoking it.

These rules govern only moldea invocation, not host-owned package-manager, planning, review, Git write, commit, or publication procedures. Git reads during explicit repair follow `project-repair.md`.

## Machine commands

Invoke the launcher with an argument array, never through a shell or package-manager command. The launcher permits only the closed commands and options below, requires an absolute repository root, requires JSON, supplies the CLI repository argument itself, and preserves the child's exit status:

```text
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- scope --paths-stdin --json --max-output-bytes 65536
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- validate --json --max-output-bytes 65536
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- inspect --json --max-output-bytes 65536
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- content --path <canonical-path> --json --max-output-bytes 65536
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- composition --json
```

`scope` is the single pre-reference relationship query, `validate` returns repository-format diagnostics, binding coverage, and integration warnings, `inspect` returns content-free inventory, `content` reads one explicit canonical asset, and `composition` is used only when installed package composition matters. The launcher's fixed 65,536-byte composition boundary replaces a caller-supplied page budget.

The gate and the launcher's `scope` and `content --path` normalize bare repository-relative paths, leading-slash repository-logical paths, leading `./`, and native absolute paths beneath the supplied or resolved repository root. Relative paths start at that root regardless of the working directory. Windows relative paths also accept backslash separators. Other POSIX leading-slash paths retain their logical meaning. Traversal, internal dot segments, repeated separators, root-only selections, outside Windows drive paths, drive-relative paths, UNC/device forms, and POSIX relative backslash paths remain errors. `content` still selects one explicit canonical asset. For stdin scope, encode each path's UTF-8 bytes followed by one NUL, never put a delimiter before the first path, and pass the complete stream once within the unchanged raw 2 MiB input limit. Never call `scope` separately per path.

## Envelope verification

The launcher verifies complete UTF-8 JSON, schema 7, the exact installed CLI version, invoked command, result/error shape, and exit/status agreement for every completed response, including calls without capture and `composition`. It preserves verified raw bytes and legitimate exit codes: 0 for `valid`, 1 for `invalid`, and 2 or 3 for `error`. Malformed or contradictory output returns 3 with a short diagnostic and no stdout. It accepts additive fields without interpreting full CLI payloads.

Signals, launcher failures, output-boundary termination, malformed output, contradictory status, version mismatch, unsupported schema, and incomplete output establish no conclusion. The launcher sends the requested termination signal first and force-terminates a child that remains active after one second. An `invalid` result is diagnostic evidence, not validity.

For `validate`, use the complete result's `diagnosticCount`, `errorCount`, and `warningCount`, and `acceptedWarningCount`; for `inspect`, use `counts.diagnostics`, `counts.errors`, `counts.warnings`, and `counts.acceptedWarnings`. The launcher verifies these nonnegative integer totals, their arithmetic, and agreement with `result.valid` and status. Totals cover the snapshot even when `page.records` has a continuation cursor; an empty page does not establish a clean result. Totals satisfy diagnostics = errors + unaccepted warnings + accepted warnings, and valid means zero errors. Warnings do not invalidate or block the project. Accepted warnings remain visible with their reason; acceptance does not establish coverage. Errors remain failures. The agent still interprets relevance, authority, warnings, completeness, and whether another page is necessary.

Every paged result carries a snapshot identity. Use launcher-owned response files to continue without transcribing opaque cursors. Create its private task-owned directory with `node <installed-skill-root>/scripts/response-directory.mjs --repository <absolute-repository-root>` and retain the returned absolute path. Use short portable filenames such as `page.json` beneath it. On POSIX it must be owned by the current user with no group/other access; on Windows use the host's private temporary storage. Hosts that prohibit scratch writes retain that constraint; report incomplete traversal instead of bypassing it.

```text
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- content --path <canonical-path> --json --max-output-bytes 65536 --save-response <absolute-temporary-file>
node <installed-skill-root>/scripts/moldea-cli.mjs --repository <absolute-repository-root> -- content --path <canonical-path> --json --max-output-bytes 65536 --cursor-from-response <absolute-temporary-file> --save-response <absolute-temporary-file>
```

These launcher-only options support `content`, `inspect`, `scope`, and `validate`, never `composition`. Each invocation fetches one page and emits the unchanged raw envelope. Repeat the same command, filters, and applicable scope input only when another page can change the conclusion. The launcher extracts the exact preceding cursor, checks schema/command/installed-version identity, and strips its file options before CLI execution. Do not combine `--cursor-from-response` with `--cursor`, reconstruct cursors, use custom parsers or loops, filter output, aggregate pages, or restart and merge snapshots. A null cursor ends traversal; requesting its continuation fails before child execution.

If the host truncates or loses a response saved with `--save-response`, read the saved file instead of rerunning the command. The read must fit the cycle's remaining tool-output budget.

Files must be absolute beneath the resolved host temporary root, outside the repository, with no linked file or directory components below that root. Input remains bounded to 1 MiB. Capture preserves complete valid/invalid response bytes and status, including diagnostic exit 1. Use a fresh target or explicitly replace the same loaded checkpoint; unrelated existing files are never replaced. Error or incomplete responses preserve the checkpoint. Cancellation prevents capture before the atomic write starts; a write already started may complete, but the invocation still fails with no stdout. Continuation shares the original call/output budget and stops once the required evidence is sufficient. Remove owned response files and the scratch directory when no longer needed, including on a controlled pause or failure unless retained to investigate an unresolved issue.

## Validation recovery

For authorized canonical writes requiring validation, complete the writes and applicable project-native checks before final launcher-backed validation. Success ends verification without unnecessary inspection. A valid result reports completed declared checks, not universal semantic alignment or runtime readiness. Use coverage counts by default, paging only the selected agent’s binding records when needed. Each record names a file/export check and its passed, failed, or not-checked status and reason; runtime wiring is never listed as checked. Interrupted inspection fails the entire operation and returns no partial coverage. Report acceptable warnings under `continuous-maintenance.md` → “Warnings and acceptance”; report final integration warnings with both `Fix moldea` and developer acceptance paths. Read-only and independent Agent Skill operations retain their own verification boundaries.

On failure, establish the complete affected contract from diagnostics and the smallest relevant evidence before editing. Inspect equivalent occurrences in the authorized change set, apply the supported complete correction, rerun native checks affected by it, and validate the resulting state. Continue while changed state and new evidence support progress; a newly exposed diagnostic can represent progress even when the diagnostic count is unchanged.

A `repository`-source error names an entry the launcher cannot read in this working tree. Report the path and stop; never validate a copy, clone, or snapshot of the repository.

Never retry unchanged input without new resolving evidence. Stop when no supported correction remains, failures repeat without progress, corrections oscillate, authority is unresolved, tooling is unavailable, the next change exceeds scope, or a real resource limit prevents completion. Reserve output capacity for final validation. After writes invalidate a snapshot, discard its cursors and obtain only necessary fresh evidence within the same budget.

Report the actual changes, final status, material diagnostics, completed checks, and remaining work. Every repair requires validation after its writes; earlier validation cannot support completion. Preserve unverified changes when recovery cannot finish and identify them as unverified.

## Resource limits

A budget covers one maintenance cycle, from the relevance check through final validation. The next developer request, including `continue`, or the next step of a multi-step request planned before execution starts a new cycle. Never autonomously start a new cycle to continue work that reached a limit. A developer request may resume that work in a new cycle; it does not extend the stopped cycle's budget. Never extend a budget within a cycle or ask the developer for an extension. In ordinary work, a reached limit never blocks the developer's task: complete the task, still run final validation for any canonical writes already made, skip further assessment reads, and report in one line which canonical checks remain for the next request. Use reserved capacity for validation; if the ordinary aggregate moldea-output allowance is already exhausted, still run one bounded final validation for those writes, without further assessment, a budget reset or another correction loop. In an explicit moldea operation such as repair or initialization, stop at the limit and report the completed work and continuation point.

Use a 65,536-byte output page for ordinary work and stop after obtaining the relevant record, diagnostic, or passage. Keep ordinary aggregate moldea output within 524,288 bytes per cycle. Explicit project repair is a `largeTraversal` operation that continues by complete owner when it reaches a per-cycle limit. It remains purpose-bounded and paginated, with each invocation below 1 MiB and within its profile's per-command output limit. The launcher rejects missing, malformed, smaller-than-4-KiB, or larger-than-1-MiB page budgets and terminates a child that exceeds the declared stdout boundary. It also bounds stderr independently.

`OUTPUT_BUDGET_TOO_SMALL` means the next complete record cannot fit and increasing the page within the 1 MiB ceiling and the active profile's per-command output limit may be appropriate when the record is necessary. `RESOURCE_LIMIT_EXCEEDED` means a compute or storage guard was reached. Verified heap exhaustion is non-retryable for unchanged input; it does not prove the application code is wrong. `INSPECTION_TIMEOUT` is an elapsed-time failure, `INSPECTION_BUSY` is capacity contention, and `INSPECTION_PROCESS_FAILED` is an operational inspection failure. Retryable metadata never authorizes an unchanged retry loop. Preserve completed corrections and report the missing inspection conclusion. Do not tune internal limits, split or delete healthy source, or silently skip files. Output pagination bounds transfer, not arbitrary source parsing. Report the observed operation, safe error code, and missing conclusion after direct activation.

Semantic evaluation records command count and emitted bytes from the completed process evidence. Host failure-containment ceilings do not define normal skill consumption and must never be presented as repository-capacity limits.

Release evaluation measures each test trial against separate source-controlled profiles (host commands, moldea calls, model tokens and tool output). Those trial measurements are not limits on the developer's task. In every operation, moldea's limits count only moldea's own work: moldea CLI calls and output, bundled helpers (including the repair Git helper), and canonical file reads and writes. In explicit repair and initialization, source reads made for that assessment count toward completed host commands and model-visible output, not the aggregate moldea-output allowance. Commands the project itself needs, including tests, builds, Git and project checks, never count, whether the work is ordinary maintenance, initialization or repair.

For explicit repair and initialization, the `largeTraversal` profile allows per cycle 64 completed host commands, 16 moldea CLI calls, 1,625,000 input-plus-output model tokens, at most 262,144 model-visible bytes from one completed host command, 1,048,576 aggregate moldea-output bytes, and 4,194,304 aggregate model-visible tool-output bytes. These limits use the counting rule above and remain separate from the unchanged 65,536-byte raw moldea CLI response-page guidance and invocation safeguards. Initialization and repair retain their existing stop-and-continue behavior.
