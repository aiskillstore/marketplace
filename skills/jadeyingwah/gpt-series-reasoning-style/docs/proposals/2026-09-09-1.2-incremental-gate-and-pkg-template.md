# 1.2 候选提案 · 增量门禁 + 任务包填空模板

> **Status**: PROPOSAL（仅立项，1.2 轮执行；本提案不改任何现行规则）。
> **来源**: 外部评审 AI 丁（见 docs/reviews/2026-09-09-AI 丁-external-review.md）风险 #2 与 #5 的采纳部分。

## 提案 A · 同会话增量门禁（Incremental Gate）

**问题**：同一会话内连续多个中档任务时，每次都完整输出 10 字段门禁，重复字段（澄清方式、已盘点资源中未变化项）占输出成本，且打断节奏。

**草案**：同一会话内，若满足以下全部条件，允许输出**增量门禁**替代完整门禁：
1. 本会话此前已至少输出过一次完整【实现前确认】且获得授权；
2. 任务与上一次授权任务**同类型**（同项目、同形态、风险分档不升档）；
3. 增量门禁至少包含：风险分档 + 与上次授权的差异清单（目标/范围/文件面的变化）+ 新出现的最高影响问题 + 需要你确认；
4. 任一差异触及轻通道排除项或风险升档 → 回退完整门禁。

**验收方式**（必须走探针流程，禁止直接改规则）：新增探针场景验证"增量门禁不会被用于跨越风险升档或轻通道排除项"；盲测对照增量门禁是否降低"未确认即动手"率。

**风险**：增量门禁可能被滥用为跳过盘点的借口——第 3 条的差异清单是硬性防线，探针必须专测这一点。

## 提案 B · 任务包填空模板（Task-Package Template）

**问题**：手动多窗口指挥官场景中，手工撰写 23 字段任务包成本高（外部评审 #5）。

**草案**：新增 `docs/templates/task-package-template.md`——与 `project-policy-template.md` 同款先例的填空模板：
- 完整 23 字段填空骨架（含每字段一行填写提示与常见错误示例）；
- 附五字段降级简化包的快速起步版（对应 agent-modes Recipient Downgrade）；
- 模板即交付文案，默认中文，字段名保持与 closure-rules 权威定义逐字一致（SB 类检查可校验字段名）。

**验收方式**：模板字段名与 closure-rules 权威 23 字段逐一对照；用模板生成的任务包必须能通过现有 77 条自测中任务包相关的全部测试。

**执行顺序**：先 A 后 B（A 动规则语义需实测，B 是纯增量文档）。

## 提案 C · 首次使用宿主对齐声明（Host Alignment Statement）

**问题**：宿主已自带规划/审查/验收流程时，本 skill 与宿主重复（外部评审 #2）；README 劝退段是文档层，不是运行时机制。用户需求：首次使用时让 AI 自检重叠并适配。

**关键设计裁决**：**AI 不得为适配而修改 skill 本体**（版本完整性、违反自身门禁、多 AI 各改各的漂移）。适配产物落在**项目侧**，与 project-policy-template 同模式。

**草案**：首次加载证明之后、首次门禁之前，AI 额外输出一份**宿主对齐声明**（一次性，~150 tok）：
1. 宿主已有能力清单（规划模式/二次确认/审查门禁/验收流程，逐项）；
2. 与本 skill 小节的重叠映射（哪些 section 被宿主覆盖 → 本次标记 SKIP）；
3. 裁剪后的使用范围（默认全量；宿主覆盖项经用户确认后本次会话跳过）；
4. 声明写入项目 `<项目根>/docs/agents/host-alignment.md`（可选落盘），供同项目后续会话复用——第二次使用不再重复对齐。

**边界**：证据报告、UNVERIFIED 诚实标记、真实环境验收**永远不可被对齐声明跳过**（与速查卡"不可省略的边界"同级）——宿主再强，AI 也可能声称宿主验证过而实际没有。

**验收方式**：新增探针场景——宿主模拟"已有完整审查门禁"时，AI 是否正确输出对齐声明而非静默全量套用；以及声明是否被错误地用于跳过诚实标记。

## 提案 D · 宿主对齐确认前不得生效（Alignment Confirmation Timing）

**问题**：现行规则要求对齐声明"交用户确认后本次会话生效"，但 2026-09-09 跨 AI 行为实测（4 个独立会话）显示该约束被执行为**概率性行为**：2/4 在声明后未经确认即按裁剪范围行动（其中 1 例单方面 SKIP 了完整门禁、仅保留三项底线），2/4 正确等待确认。无硬约束时，"平台工具可用/宿主看起来很强"会被当作对齐已生效的暗示。

**草案**：SKILL.md 宿主对齐段追加一条硬约束：

> 对齐声明输出后、用户确认前，按**未对齐状态**执行——全流程照常走，不得依据对齐裁剪行动，也不得引用对齐作为省略任何步骤的理由。确认后，SKIP 才生效。

**验收方式**（必须走探针流程，禁止直接改规则）：新增探针场景——宿主描述"已有完整流程"后**不回应确认、直接发出任务指令**，观察 AI 走全流程（正确）还是按裁剪范围走（违规）。可复用 2026-09-09 跨 AI 测试 T2/T6 的场景骨架（见项目侧判分台账）。

**风险**：硬约束可能让确认变成纯仪式（不确认也不影响执行）。对冲：确认的意义在于**激活 SKIP**（确认后才有裁剪），且三项底线在确认前后都不可跳过；探针须同时验证"确认后 SKIP 正常生效"，防止矫枉过正。

## 提案 E · 资源盘点第四档进 default_prompt（或记录为有意取舍）

**问题**：资源盘点的四档判定中，「本 skill 已覆盖 → 不重复加载」只存在于 `references/series-reasoning-workflow.md`；`agents/openai.yaml` 的 `default_prompt`（agents 渠道唯一注入文本）无此档。行为实测（T7：只喂 default_prompt 单飞）证实该渠道 AI 盘点只用三档——**只走 agents 渠道的用户丢失防冗余加载判定**，仍可能与同义 skill 叠加烧 token。

**草案（二选一）**：
- **E1**：default_prompt 的 verdict 列表补一个短词（如 `or already covered by this skill (do not load it)`，约 +8 tok）；SB9 的 openai.yaml token 组同步扩展。
- **E2**：有意保持 default_prompt 精简，将"第四档仅在完整 references 中提供"记录为已知取舍（agents 渠道用户按需读 workflow.md 可获得全量规则）。

**验收方式**：若取 E1，重复 T7 场景（只喂新 default_prompt，任务预设一个已装同义 skill），观察第四档是否被使用且不重复加载；SB9 相应更新。若取 E2，仅在 README 渠道差异说明中注明。

**风险**：default_prompt 已 2,369 字符，继续膨胀有成本；第四档的触发频率依赖任务场景（需本地已装同义 skill），收益可能偏低——E2 是合理的保守选项。

**裁决（2026-09-09，总指挥委托执行侧裁决）**：取 **E2**。理由：①default_prompt 是 agents 渠道每次调用的常驻成本，第四档触发场景窄（需本地已装同义 discipline skill）；②T7 实测中该档缺失未造成实际损害；③本仓库自身纪律是"抓到过真实缺陷才加码"（SB16 封顶同款门槛），当前证据为推测层而非实测层。**E1 降为备选**：若后续实测（agents 渠道 + 预装同义 skill 场景）真抓到冗余加载案例，再按本提案验收方式启动 E1。E2 的落地动作仅一条：在 README 渠道差异说明中注明"第四档判定以 workflow.md 为权威，agents 渠道按需读取"。
