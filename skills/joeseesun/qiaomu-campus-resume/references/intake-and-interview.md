# 对话式访谈与采集

这不是一次性问卷。目标是在自然对话中把学生真正做过、能解释、可确认的经历变成简历事实。借鉴 Grill Me 的“一次一个问题、附当前判断、沿分支深挖”，但语气必须友好、具体，不审讯、不制造压力。

## 入口判断

先识别用户已提供的旧简历、岗位 JD、成绩单、项目说明、竞赛证明、GitHub 或作品链接。只读取用户明确放入范围的材料。

- 有旧简历：先提取并复述已知事实与最影响定位的缺口，不重新询问已写明的信息。
- 无旧简历：从目标岗位开始，用聊天方式逐项建立事实账本。
- 有 JD：优先追问决定“是否匹配、如何排序、需要删除什么”的事实。
- 无 JD：从证据推断 1 个默认岗位方向，最多给 2 个备选；只有选择会改变内容时才让用户决定。

### 旧简历纯排版快速路径

用户明确说“内容不改”“只美化”“只重排”“换个模板”时，不启动完整 Grill Me 访谈：

1. 运行 `extract_resume.py`，保留原文件并输出本地提取文本；
2. 用不超过 8 条复述姓名、联系方式、教育、经历、项目、技能、时间线和明显矛盾；
3. 只问一次“以上事实是否按原简历直接排版”，遇到阻断矛盾时改问最关键的一个问题；
4. 把原文事实转换为 `resume-data.json`，每条 bullet 使用 `source_resume`，不主动补数字、职责或成果；
5. 运行 `validate_resume.py`，生成一套岗位合适的默认主题；用户明确要多种风格时才生成六套。

排版快速路径不要求为了换模板重新形成两项深度证据闭环。用户一旦要求“帮我把内容也写得更好”“针对 JD 改”，立即切换到内容优化或 JD 定制流程。

### JD 定制路径

同时读取 JD 与旧简历或访谈事实，把 JD 拆成必备条件、加分项、职责和自然关键词。先给出简短的 `要求 → 已有证据 / 缺口 → 简历位置` 摘要，再追问一个最影响匹配度的证据缺口。没有证据的要求保持 `gap`，不得把它写进技能栏或经历 bullet。只有 JD、没有旧简历时，仍从零问答，但优先收集能证明必备条件的经历。

## 对话协议

### 每轮只问一个核心问题

一条消息只推进一个决策或一段经历。问题可以带 1–2 个帮助回忆的提示，但不能并列成表单。

推荐格式：

```text
当前判断：我认为你最值得深挖的是 <经历>，因为它最能证明 <岗位能力>；如果判断错了请直接纠正。

先问一件事：在这段经历里，你本人独立或主要负责的部分是什么？
```

不要用“请填写学校、专业、电话、邮箱、项目、技能……”一次索取全部字段。用户主动一次回答很多时，要全部吸收，跳过已覆盖问题。

### 问题必须附当前判断

用户通常更容易纠正一个具体判断，而不是从空白开始组织答案。判断必须说明依据，并允许被推翻；不得用判断诱导用户认领团队成果或不存在的数字。

错误示例：

> 你把性能提升了 50% 对吗？

正确示例：

> 当前只能确认“完成并通过验收”，还没有性能数据。你是否记录过耗时、错误数、测试数或覆盖范围？没有也可以，我们就写完成度而不写百分比。

### 沿一项经历深挖到底

对最强经历按 A-C-R-E 顺序追问，形成闭环后再换下一项：

1. **情境与范围**：何时、在哪里、为谁解决什么问题；团队或课堂规模如何。
2. **个人边界**：本人负责什么，哪些是团队共同完成，谁做了其他部分。
3. **关键行动**：做了哪些具体动作、技术决策、内容设计或协调工作；为什么这样做。
4. **难点与取舍**：遇到什么约束，尝试过什么，为什么选择最终做法。
5. **结果与交付**：上线、验收、演示、获奖、交付物、范围或前后变化。
6. **证据与可解释性**：结果从哪里得知；面试时能否解释过程、原理、权衡和个人贡献。

不是每层都必须单独问。用户已自然覆盖的层级直接记入账本；只追问仍会改变简历表达的缺口。

### 定期复述，不偷偷补全

每 2–3 轮或完成一项核心经历后，用不超过 5 条复述：

- 已确认事实；
- 仍不确定或相互矛盾的地方；
- 下一步最值得问的问题。

复述不能把推断改写成事实。发现时间、角色、项目归属或数字矛盾时要直接指出，并请用户选择或更正。

## 事实账本

对话过程中在用户工作目录维护 `interview-ledger.json`。它是本地私有工作文件，不进入公开 PDF。建议结构：

```json
{
  "version": 1,
  "target": {"role": "后端开发实习", "jd_available": true},
  "job_requirements": [
    {"requirement": "使用 Python 开发接口", "priority": "must", "evidence_ids": ["project-api"], "status": "supported"}
  ],
  "basics": {"name": "姓名", "phone": "手机号", "email": "邮箱"},
  "education": [
    {"school": "学校", "major": "专业", "degree": "本科", "start": "2023.09", "end": "2027.06"}
  ],
  "evidence_items": [
    {
      "id": "project-api",
      "kind": "project",
      "name": "课程 API 项目",
      "start": "2025.03",
      "end": "2025.06",
      "ownership": "独立负责接口与测试",
      "problem": "为校园活动报名流程提供稳定 API",
      "actions": ["实现核心接口", "补充自动化测试"],
      "methods": ["使用 FastAPI 与 PostgreSQL 建模并实现权限校验"],
      "result": "通过课程验收",
      "proof": "课程验收记录与仓库提交",
      "skills": ["Python", "FastAPI"],
      "status": "confirmed"
    }
  ],
  "skills": [
    {"name": "Python", "evidence_ids": ["project-api"], "status": "confirmed"}
  ],
  "uncertainties": [],
  "confirmation": {"status": "confirmed", "confirmed_at": "2026-08-04"}
}
```

`proof` 可以是用户确认、原简历、仓库、证书或正式文档，不要求全部上传。`job_requirements` 不是关键词清单：每项必须关联证据或标记 `gap`，不得为了把状态改成 `supported` 而诱导用户认领未做过的技能。不得在账本中保存身份证号、密码、令牌、完整住址或无关隐私。

## 生成就绪门禁

从 0 创建、内容优化或 JD 定制在生成最终简历前运行：

```bash
python3 scripts/assess_interview.py interview-ledger.json
```

只有以下条件全部通过才是 `ready`：

1. 目标岗位明确；
2. 姓名、电话、邮箱完整；
3. 学校、专业/学历、毕业时间可确认；
4. 至少两项岗位相关证据形成“个人贡献—行动—结果—证据”闭环；
5. 至少一组技能能关联到具体证据项，而不是孤立罗列；
6. 没有阻断性的时间线、归属或数字疑点；
7. 用户明确确认最终事实摘要。

稀疏经历的学生可以把课程设计、科研、竞赛、校园实践、志愿服务或高质量个人作品作为证据项，不得为了凑两项而编造。

纯排版快速路径不运行 `assess_interview.py`，但必须同时满足：旧简历提取成功、事实摘要获得用户确认、所有经历 bullet 使用 `source_resume`、`validate_resume.py` 通过。任何事实矛盾、占位符或缺失联系方式仍会阻断“最终可投递”声明。

## 最终确认

门禁接近通过时，向用户展示简短事实摘要：

```text
目标岗位：...
主打经历：...
可使用的数字/结果：...
技能证据：...
准备舍弃：...
仍有疑点：无 / ...

以上事实可以作为最终简历依据吗？需要改哪一项？
```

“你看着办”“应该可以”“随便”不是事实确认。此时应把最关键的两种解释说清楚，让用户纠正；不要无限追问。明确的“确认”“这些事实没问题”“按这个生成”才通过确认门禁。

## 退出与降级

- 用户可随时说“跳过”“不知道”“停止采访”或“先出草稿”。
- 跳过非关键字段：继续下一高价值问题，并在摘要里标记缺口。
- 关键事实不足：交付已确认事实与下一步问题；可以生成标注为草稿的 JSON/HTML，但不把 PDF 报告为最终可投递版。
- 用户明确要求立刻生成：尊重其节奏，但仍需列出阻断缺口和不可验证内容；不得用模型推断补齐。
- 连续三轮没有新增事实：停止重复追问，说明卡点，换成更具体的回忆提示或建议用户提供材料。

## 隐私边界

- 默认不收集身份证号、性别、婚育、民族、宗教、完整住址和照片。
- 联系方式、私人仓库与原始访谈只保存在用户指定的本地工作目录。
- 不把个人资料、简历或 JD 上传到第三方服务，除非用户明确授权具体服务与用途。
