# 按需评审架构

[English](review-architecture.md)

仅在 Birdview 已激活且用户要求评估架构或寻找重构机会时使用。从[阶段 1](map-project.zh.md)核验过的地图出发，评审用户指定范围，不默认扩大到整个仓库。

## 检查职责

存在相关项目术语和架构决策时先阅读；缺少术语表或 ADR 不代表需要创建。追踪候选模块的调用方与实现，寻找具体问题：

- 一个职责需要跨多个模块协同修改，或调用方必须了解内部顺序、错误处理、配置细节。
- 包装层没有增加多少行为，却多引入一层接口。考虑移除它后复杂度是消失了，还是转移到调用方；小型适配器也可能有存在价值。
- 现有边界让重要行为难以通过公开接口验证。说明受影响的行为，不要求为每个实现细节编写测试。

优先考虑让调用接口更简单、相关行为更集中的改动。模块数量、文件大小和图是否整齐本身不构成问题证据。尊重已有架构决策；只有具体的新证据才支持重新讨论，并应明确指出冲突。

## 提出有依据的候选方案

仅返回有依据的候选项，按预期价值排序。每项说明：

- 现有模块 ID、源码路径/符号、观察到的问题及实际影响。
- 拟议职责或依赖变化、预期收益、迁移成本和风险，包括保留现状的理由。
- 面向行为的验证计划及判断强度：证据充分、值得调查、推测。指出缺失证据，不把假设当成缺陷。

通过现有 Birdview 预览定位涉及模块，在图旁的说明中解释候选方案。正式地图保持真实：不把现有关系替换为提案，不编造活动事件，不把对照视图当作架构修改前后差异图。在配套说明中描述拟议结构，无需另建报告框架或扩展 Schema。

仅在证据支持时推荐优先候选项；没有值得重构的内容也是有效结论。先查清源码能回答的问题，再询问实质性的产品或设计选择，并给出建议及取舍。仅评审不授权实施。获得实施授权后，使用当前地图和声明范围进入[阶段 2](show-changes.zh.md)；已有授权不重复询问。
