# 阶段 1：建立项目地图

[English](map-project.md)

为选定项目与范围生成符合 [Schema](../schemas/architecture.schema.json) 的架构 JSON，以及由同一数据渲染的独立 HTML。遵循[语言规则](bilingual.zh.md)；示例仅用于参考字段，其虚构系统不是项目证据。

## 发现与核对覆盖

1. 依次检查用户提供或文档指定的架构路径、现有产物位置、`.birdview/`、根目录和 `docs/`。限定 architecture/map 文件名搜索，排除依赖、生成输出与技能示例；这些位置及引用均无结果时才扩大搜索。
2. 阅读候选内容，核对项目相关性、覆盖范围、当前归属与源码证据。校验 Birdview JSON；Schema 有效不证明数据最新。优先用户选择或文档指定的权威地图，仅在候选冲突无法解决时询问。
3. 在原位置复用兼容地图，更新过时部分。其他格式经源码核对后转换，保留有意义的 ID 和原产物。仅有 HTML/图片时，阶段 2 前先补齐模块与归属数据。没有可复用或调整的地图才新建；阶段 2 前必须解决无法运行校验的问题。
4. 遵循明确子系统范围，否则检查选定项目根目录。阅读根文档、顶层目录和相关工作区/构建清单，沿声明的应用检查各自清单、启动/构建入口与源码。依赖本身不能证明应用存在；确认客户端与服务端连接前先追踪调用和路由。
5. 新地图与复用地图都须将范围内每个应用对应到模块、得到解释的分组或明确覆盖缺口。职责独立的应用保持可见，共享包不必算应用。6–10 个模块只是可读性目标，不能因此遗漏或编造。
6. 普通局部编辑复查相关入口和变化清单，范围或工作区结构变化时才扩大检查。在架构表旁说明根目录/范围、已查应用及模块 ID、排除项和未解决区域。区分未检查与已检查但未发现；零不确定性不证明完整覆盖。

## 编写地图

沿主要请求/数据路径追踪，阅读符号上下文后确定职责。针对局部代码，在约定范围内向上理解其职责及相关调用方/依赖；范围可被连贯描述时停止。

模块表示内聚的业务或技术职责，保持可比较的抽象层次，不按文件、类或目录逐个建节点。说明各模块做什么、如何连接周边模块，具体实现位置放入归属/证据。有项目领域术语表时沿用，否则使用源码和文档中的既有术语。优化名称时保留有证据支持的职责边界与现有 ID。

字段、角色、归属、证据、状态与布局遵循[契约](contract.zh.md)。模块角色依据已检查职责，不明确用 `generic`，不为配色轮换；角色独立于归属与分组。外部服务仅用于解释真实关系，不分配本地文件归属。无充分支持的结论标为 `uncertain` 并列出具体问题；`supported` 表示检查过证据，不是静态证明。

新地图须逐模块显式分类，渲染前运行 `node <skill-root>/scripts/validate.mjs <map.json> --authoring`（中英双语交付追加 `--bilingual`）。通用模块按契约填写 `roleAssessment`，说明现有类别为何不适用或缺少什么证据；证据不足须标待确认并给出具体问题。不得为省事批量使用 generic。全通用提醒须逐模块结合源码复核并报告原因，不为过检查编造不同角色。复用时保留已有分类，仅在新证据支持时更改；降为通用须说明理由并遵循版本规则。更新旧地图时核对新增/变化模块的分类，不强制迁移未变化的旧字段。

有向关系填写具体标签、证据、状态、`kind` 与 `visibility`。核心执行、必要结果/工具反馈、基础依赖和必需审批放在 `overview`；恢复、重试和诊断可放在 `detail`，除非它们就是主题。不明确时用 `overview`。检查孤立概览模块是否缺少连接，保留真正的辅助模块及隐藏关系计数。所有关系保留在数据中；类型/可见性不代表修改范围，也不能仅为减少拥挤而改变。

从同一 JSON 展示架构表（模块、职责、归属、证据、不确定性）和简短关系列表。允许用户纠正，已授权继续时不重复审批。

## 分组与版本

仅为有证据的系统/子系统成员关系建立可选分组：单层、成员不重叠，包含稳定 ID、名称、唯一成员和非空证据。分组并排展示，保留组内行列顺序，未分组模块位于外框之外。组名和证据采用模块的翻译规则。

依据源码支持的职责选择分组角色，并在证据说明中解释分类：

| 角色 | 含义 | 固定色系 |
| --- | --- | --- |
| `interaction` | 用户交互与审阅 | 淡蓝 |
| `runtime` | 执行与调度 | 淡暖黄 |
| `external-services` | 所描述系统之外的集成 | 淡紫 |
| `generic` | 未指定或混合职责 | 中性灰 |

不明确或省略时用 `generic`。名称、顺序、模块归属和颜色多样性不是分类证据。分组角色不代表模块角色、部署/信任边界或活动状态。沿用共享调色板，不为单图覆盖或添加颜色字段。Schema 拒绝未知角色/字段但不能验证分类真实性；检查证据，仅在新证据支持时更改已有角色。

替换前阅读现有产物，使用约定位置（默认 `.birdview/`），不覆盖无关文件。`project.id` 与 `mapId` 是本地标识，不必为 URL。可选 `project.revision` 记录 Git 提交，不是地图版本，也不保证工作区干净。

每次保存地图变化（含布局和翻译）均增加 `revision`。职责持续时保留 ID，不将已移除 ID 分配给其他职责。先在旧地图上完成/取消任务，再针对新版本启动；不得静默重放旧事件。

## 渲染与检查

默认“使用 Birdview”交付时，最终渲染前完成[约束流程](constraint-graph.zh.md)：检查生效本地指令、收集已提交来源、撰写并审查 `reviewed-rules.json`，再携带仓库参数编译，采集规则历史到 `.birdview/constraints.reviewed.json`。工作区指令差异须明确列为限制。按[约束契约](constraints.zh.md)在 `map.constraintDiscovery` 记录实际已检查和未检查路径；扫描不等于语义审查。不得复制演示规则。有效时复用匹配的已审查清单。明确范围与快照，检查来源后才能关联模块。来源清单、审查选择与编译后的清单一起保存，供其他 AI 继续审查。审查未完成时报告边界，不得声称完整交付。没有已审查规则时，交付架构与发现结果并注明限制；规则渲染器有意拒绝空清单或未经审查的清单。

使用自带渲染器；从用户项目运行时用绝对路径，`<skill-root>` 是包含 SKILL.md 的目录。按实际约定位置替换路径：

```sh
node <skill-root>/scripts/render.mjs <project-root>/.birdview/architecture.json <project-root>/.birdview/architecture.html --constraints <project-root>/.birdview/constraints.reviewed.json
```

仅在明确的仅架构请求或已披露规则清单不可用时省略 `--constraints`。检查最终页面具有架构/约束切换、来源依据、规则版本标识和来源索引链接，并一起交付 `.sources.html` 文件。架构检查面板只统计架构数据中的规则，不统计独立清单；缺少模块关联不等于项目没有规则。

渲染器校验 JSON 后输出自包含 HTML，无需服务器/网络资源。不要手写替代查看器或用虚构演示充当项目地图。

在可见浏览器预览中打开 HTML。Codex `open_in_codex` 使用 `browser` 目标和正确编码的文件 URL，不用 `file` 目标。Markdown 链接可能打开源码；排队请求不证明已显示，无头检查不证明用户可见标签已显示。

在用户可用视口检查最终 HTML：

- 查看概览与全部关系、名称、关系和选中模块证据。悬浮直接关系最多的模块（入边加出边，自环一次），再检查其他明显拥挤区域。
- 检查穿卡/重叠线路、拥挤转角、端点/箭头可辨性、路径/标题裁切、隐藏关系计数和全图适配后的字号。
- 确认悬浮时直接关系可追踪，离开后恢复所选视图且节点不移动。

自动间距不保证可读性，不在地图数据添加像素阈值或拥挤度字段。必要时按职责/交互顺序调整布局、按证据调整分组；保留标识、归属、关系语义与完整范围。增加版本、重新渲染并复查受影响区域及全图。连续两次无可见改善时停止并报告剩余问题。地图未变化的局部任务无需无关 UI 审计。

报告实际产物、视口、模式、重点模块和未解决问题。Schema、碰撞抽样或截图本身不等于视觉验收；当前未内置自动拥挤检查。浏览器检查不可用/被拒绝时，说明未做视觉审查及真实限制，提供 HTML 绝对路径，解释浏览器显示图、编辑器显示源码。不得绕过拒绝，也不凭空归咎模板。

交付先给 HTML 与预览结果，再补充 JSON 路径、`project.id`、`mapId`、`revision`、覆盖范围和不确定项。修复或报告渲染阻塞；仅 JSON 不算完成可视化交付。这是快照，不是实时活动。未提供编码任务时，交付后停止并询问预期修改。有编码任务时，按[阶段 2](show-changes.zh.md) 准备并渲染范围，等待用户确认已展示方案后再实施。渲染成功本身不是编辑许可。
