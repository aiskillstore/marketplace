# Workers

Risk is a billable operation multiplied by trigger count, amplification and runtime. Binding presence alone is not a finding. All rules below are static-source candidates, not account checks; runtime evidence is used only if the user separately supplies a redacted sample.

## Meter and applicability boundary

- **Units:** On Workers Standard, distinguish inbound Worker requests from CPU time. Cloudflare says Worker-initiated Fetch/API subrequests are not billed as additional Workers requests, although they count against subrequest limits; redirects can add subrequests. A request that hits another Worker is a separate target invocation unless it is a Service Binding call covered by the Standard rule below. Worker cache hits still count as requests.
- **Service Bindings:** Under Standard pricing, an HTTP/RPC call through a Service Binding adds no request fee beyond the initial Worker request, while CPU used across both Workers is counted. On deprecated Bundled/Unbound models, each target invocation is charged as a request. Confirm the usage model and call path; a binding declaration alone does not establish that a code path runs.
- **Separate limits:** Subrequest and Service Binding invocation limits are execution limits, not billable-request counts. Do not equate a limit breach with a price unit.
- Official basis: [Workers pricing: Workers and Service Bindings](https://developers.cloudflare.com/workers/platform/pricing/#service-bindings) (CF-DOC-WORKERS-PRICING), [Workers limits: subrequests](https://developers.cloudflare.com/workers/platform/limits/#subrequests) (CF-DOC-WORKERS-LIMITS), and [Service Bindings: limits](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/#limits) (CF-DOC-WORKERS-LIMITS related page). Checked 2026-10-12. No rate is fixed here.

## CF-WORKERS-REQ-AMPLIFICATION — repeated external or scheduled work
- Risk conditions: a reachable route or autonomous trigger performs a billable request/CPU path repeatedly or fans out without a bounded quota, batch, concurrency or deadline.
- Check: trace route/hostname/Cron/queue callback → handler → fetch/storage/model call; identify public exposure including workers.dev and preview/version hostnames. Look for fixed-interval polling, retry loops and N×M fan-out. Separate billable inbound Worker invocations from ordinary outbound subrequests and other products' meters. A request map and explicit cache-hit proof can clarify paths; distinguish source/local evidence from a deployed configuration and actual production observations. If estimating scenarios offline, label traffic and request-rate inputs as assumptions supplied by the user; do not invent expected load from code shape.
- Mitigation and trade-off: add auth/rate limits, idempotency, batch/concurrency/deadline ceilings and bounded retries. For a shared quota, verify the server-side authority actually serializes/transactions the read-and-reserve path; KV-only read-modify-write is not a strict cross-caller or cross-location cap. A coordinator adds its own requests/storage and may become a per-key bottleneck; limits can reject legitimate traffic or delay work, while CPU caps only bound one invocation. See the current [KV consistency model](https://developers.cloudflare.com/kv/concepts/how-kv-works/) and [Durable Objects storage transactions](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), checked 2026-10-12.
- Blind spots: source cannot establish deployed traffic, actual usage, plan, billable path reached at runtime, or account cost. A cache hit may still invoke a Worker.
- Evidence: caseId enzyme-dev-workers-sitemap-polling; guideIds davezfr-four-layer-cost-protection, cloudflare-cost-playbook; official sourceIds CF-DOC-WORKERS-PRICING, CF-DOC-WORKERS-LIMITS, CF-DOC-KV-FAQ (related page CF-DOC-KV-CONSISTENCY), CF-DOC-DO-BASE (related page CF-DOC-DO-STORAGE). Checked 2026-10-12. The community playbook informs request mapping/scenario separation; it does not validate assumed or live traffic.

## CF-WORKERS-RECURSIVE-FETCH — recursive or cyclic Worker invocation
- Risk conditions: a handler can call its own route or trigger another Worker which calls back, with no depth, idempotency or stop guard.
- Check: search fetch/service binding targets, environment-specific URLs, event callbacks and queue handoffs; follow the full directed call chain. Distinguish ordinary external `fetch()` subrequests from a request that reaches another Worker, and distinguish public-URL HTTP calls from a configured Service Binding. Confirm plan/usage model before counting a Service Binding target as a separate request; its subrequest/invocation limits are not billing units.
- Mitigation and trade-off: break the cycle, add a bounded depth/job ID, deduplicate and cap retries/fan-out. Breaking recursion may interrupt expected workflows.
- Blind spots: URL indirection and deployed routes may not be visible in source; do not infer a live loop from a static reference alone.
- Evidence: caseId goteap-workers-queues-loop (author-reported cross-service loop; not independent diagnosis); guideId layercache-cloudflare-cost-guard-skill; official sourceIds CF-DOC-WORKERS-PRICING, CF-DOC-WORKERS-LIMITS, CF-DOC-BILLING-BUDGET-ALERTS.
