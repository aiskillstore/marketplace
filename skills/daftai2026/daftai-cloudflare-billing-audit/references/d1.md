# D1

Default scope is offline, read-only source review; do not query a live account. Use runtime metrics only if the user separately supplies redacted evidence. A binding is not a risk finding by itself. Trace query shape, trigger frequency, rows scanned/read, rows written and storage.

## Meter and query-plan boundary

- **Units:** D1 queries can count rows read, rows written, or both. Reads count rows scanned regardless of row size, not just rows returned; writes include `INSERT`, `UPDATE`, and `DELETE`; DDL may contribute reads/writes. Storage is based on stored data over time, and tables plus indexes count. D1 has no per-hour compute meter or data-transfer charge; Worker CPU for code calling D1 is a separate Workers meter.
- **Index trade-off:** an index can reduce scanned rows for indexed filters but adds writes when those indexed columns are changed. A `CREATE INDEX` in a `.sql` migration is evidence of intent only, not proof it was applied or selected by a deployed plan.
- Official basis: [D1 pricing: billing metrics](https://developers.cloudflare.com/d1/platform/pricing/) (CF-DOC-D1-PRICING) and [D1 metrics and analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/) (CF-DOC-D1-METRICS). Checked 2026-10-12. No rate or monetary estimate is fixed here.

## CF-D1-UNBOUNDED-READS — hot scans or read amplification
- Risk conditions: frequently invoked query scans a growing/large table, repeats full-table aggregates, or lacks selective indexes/pagination.
- Check: route/job → SQL query; inspect filter/order columns, `.sql` migrations for `CREATE INDEX`, EXPLAIN/query plans if provided, read loops, crawler/public fan-in, and row-count bounds. Distinguish a cap on the entire table from a cap on only pending/active rows: completed/history rows can still accumulate and keep a hot scan or aggregate growing. A migration declaring an index does not prove it was applied or selected by the deployed query plan; a SQL LIMIT can bound returned rows without bounding rows scanned. Scanner-surfaced SQL is auxiliary evidence only: do not treat an omitted file or incomplete lexical match as proof that an index is absent. Use plan/runtime row evidence only if separately supplied and redacted.
- Mitigation and trade-off: index selective filters, bound result sets, paginate, cache aggregates or reduce trigger frequency. Indexes use storage/write work; caching can return stale data. A proposed index benefit needs query-plan or redacted runtime evidence.
- Blind spots: source review cannot prove production row counts or that a plan is deployed; use runtime metrics only if the user separately provides redacted evidence.
- Evidence: caseIds darylginn-d1-missing-index, shivek-khurana-d1-reads; official sourceIds CF-DOC-D1-PRICING, CF-DOC-D1-METRICS.

## CF-D1-REPEATED-WRITES — duplicate writes or unbounded bulk jobs
- Risk conditions: recurring sync/import/migration rewrites already-present rows, has no progress checkpoint, or can repeat the full batch after retry.
- Check: trigger → insert/update/delete count; verify idempotency key/unique constraint, batch bound, progress checkpoint and retry behavior.
- Mitigation and trade-off: deduplicate/upsert, persist progress, cap batch/concurrency and add a stop/resume boundary. Smaller batches take longer and may require resume logic.
- Blind spots: a large one-time operation is not automatically runaway; measure if runtime evidence is separately supplied.
- Evidence: caseId imselmon-d1-write-volume (author-reported high writes; not source diagnosis); guideId d1-billing-circuit-breakers; official sourceIds CF-DOC-D1-PRICING, CF-DOC-D1-FAQ.

No database size or normal request count alone establishes a cost risk.
