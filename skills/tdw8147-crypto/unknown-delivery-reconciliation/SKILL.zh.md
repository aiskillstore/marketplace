# 未知投递结果核对

别把“报错了，再发一次”当结论；交付一份记录，说明原请求发生了什么、还差什么证据才能结案。

## 什么时候用

- 上传超时，但服务器可能已经受理。
- 渠道显示 `sent`，用户要求的是 `delivered`。
- 两个状态页说法不同，或用不同标识指向疑似同一个请求。
- 有同名替换附件，需要核对回执对应哪份提交字节。
- 暂时打不开回执后台，但经办人现在就需要结论。

## 什么时候不用

- 正在准备尚未尝试过的首次投递。
- 原请求已有达到要求的可信回执，直接结案，不重开。
- 还没提交，要确认的是表单输入有没有生效。
- 用户需要的是通用集成设计，不是核对一次已有尝试。
- 只是在查本地草稿保存报错，与外发无关。

## 核心规则

1. **按现有证据先交记录。** 少几个字段也能先给出可用结论。
2. **同一意图绝不重放。** 换标识、用原标识重投、再点一次测试，都可能重复已经生效的请求；别假定远端幂等。
3. **按提交时的身份核对。** 目标、时间和提交字节指纹可区分相似请求及同名替换件。
4. **优先最新的匹配正式记录，不是时间最新就算。** 别的目标或未关联的请求再新，也不能说明原单发生了什么。
5. **不同回执层级分别报告。** 渠道的受理、发送、送达、已读可能发生在不同阶段，不能向上推定。
6. **弱反证不等于确定失败。** 超时、可能受理后报错、本地计数为零或查无记录，都可能与远端已生效同时发生。
7. **关键冲突解不开就写未知。** 即便现在定不了，也能给一个有界的原单查询动作。
8. **达到用户要求就停。** 只要求送达，不再加等已读的待办。

## 工作流程

### 1. 写清用户要验收什么

- 用用户的说法记录验收层级。
- 有渠道定义时，把验收层级和原始状态对应起来。
- 找不到定义就保留原标签，并注明定义未提供。
- 区分记录已提交与被核对的业务请求已投递。

### 2. 确认是哪一次尝试

- 写标识、目标、提交时间和提交时的内容或附件指纹。
- 缺项标“未提供”。
- 超时或观察时间单列，不充当提交时间。
- 不拿新文件哈希、同名文件或相似正文顶替。

### 3. 先按身份归属，再比时间

- 记录观察时间、入口和原始状态。
- 对上原请求身份后，再比哪条更近。
- 将其他请求、其他收件方和范围外记录单列。
- 可能是别名但没有映射证据时，保留缺口，不认作同一条。
- 说明是实质冲突，还是不同对象各有一条回执。

### 4. 只下证据支持的结论

- `accepted`：渠道接收了请求，以其定义为准。
- `sent`：渠道已发出，以其定义为准。
- `delivered`：目标端按渠道定义已收到。
- `read`：渠道明确报告已读，不从送达推断。
- `明确未发生`：有权威证据证明原请求未发送；弱反证不能单独定论。
- `结果未知`：身份、状态或关键冲突还未解决。

### 5. 结案，或只留一个有界查询

- 达到要求就写无下一动作。
- 未达到时，只列一个原请求查询，写明次数或到期点与停止信号。
- 无查询能力就先交记录；写“建议查询”，不写成已查。
- 模拟任务只用给定资料，不联系真实渠道。
- 有草稿与提交工具时，先写完整记录，再同轮顺序提交。

## 输出模板

```markdown
# 原请求投递核对｜[请求]
验收要求：[渠道层级／证据]
原请求：[标识]｜[目标]｜[提交时间]｜[提交指纹]

## 最近相关观察
- [查询时间]｜[入口]｜[原始状态]｜[渠道定义]
- 身份匹配：[回执如何归到原请求]
- 排除或待定：[其他记录，以及为什么不能据此定论]

## 结论
- [已受理／已发送／已送达／已读／明确未发生／结果未知]
- 验收：[已达成／未达成／未验证]，因为[证据和缺口]

## 下一步
- [结案，无动作] 或 [一次原单查询方案＋上限＋停止信号]
- [如适用：建议，未执行]
```

找不到字段就写“未提供”，其余照常交付。

## 完整示例

### 示例一｜最新那条是别的目标

**输入。** 10:14 UTC 提交给 `review-east` 的上传 `u-82` 超时，哈希 `9cf`。
10:16 原状态页对同目标、同哈希报告 `delivered`。
10:17，另一条发往 `review-west` 的请求显示 `sent`。用户只要求送达。

**反例**

> 最新是已发送。等已读吧，或者保险起见再传一份。

**正例**

> 原请求：`u-82`｜`review-east`｜10:14 UTC｜哈希 `9cf`。
> 最近相关观察：10:16 UTC 原状态页显示 `delivered`，渠道定义为目标端收到。
> 10:17 的 `sent` 目标是 `review-west`，不能覆盖匹配的回执。
> 结论：已送达，达到验收。结案，无下一动作，不等已读。

**为什么能用。** 先认身份，再看新旧；达到要求的层级就关单。

### 示例二｜超时后出现同名替换 PDF

**输入。** `p-31` 在 16:03 UTC 发往 `proof-queue`，提交 `proof.pdf`，哈希 `0b4`。
本地客户端超时，计数为零。面板按文件名搜到已发送记录，但哈希为 `21a`。
尚未查过原请求状态页。用户要求确认送达。

**反例**

> 本地是零，肯定没发出去。不过已发送里有同名文件，就标送达吧。

**正例**

> 原请求：`p-31`｜`proof-queue`｜16:03 UTC｜哈希 `0b4`。
> 最后观察：本地超时、计数为零；观察时间未提供。两者都不能证明远端失败。
> 面板 `sent` 行对应哈希 `21a`，不是原提交字节；`p-31` 没有匹配的回执定义或层级记录。
> 结论：结果未知，送达未验证。
> 仅建议：在原状态页查一次 `p-31`。匹配回执显示送达或达到查询上限即停止；仍无结论就保留未知。不重发。

**为什么能用。** 文件名一样，不能把两份不同内容的投递证据混用。

## 常见错误与警讯

| 警讯 | 应该怎么写 |
|---|---|
| “同标识再发很安全” | 原标识用来查，不用来重放。 |
| “文件同名，附件就一样” | 对照原提交时的指纹。 |
| “搜不到就没发生” | 写查过的入口，除非有更强证据，否则保留未知。 |
| “已发送就够了” | 把渠道定义的层级与用户要求对照。 |
| “以最新一条为准” | 先对目标、时间、指纹和原请求身份。 |
| “继续轮询直到有结果” | 写次数或期限；到上限仍无结果就保留待决。 |

## 交付前自检

- [ ] 写明了用户要求的验收层级。
- [ ] 原标识、目标、提交时间和指纹都有记录或标为缺失。
- [ ] 提交与观察时间分开。
- [ ] 最近相关回执有原始标签和渠道定义，缺定义就标明。
- [ ] 不用不匹配或未归属的证据撑结论。
- [ ] 不靠弱反证把未知改成明确未发生。
- [ ] 只有一个有界原单查询，或已明确结案。
- [ ] 建议操作没写成执行过，也没有重放请求。

## 交付即止

交付核对记录，不执行首次投递，也不重发；提交记录和投递业务请求是两件事。
模拟任务只把下一查询写成建议，不联系真实渠道。
