# 发布记录模板

复制到被发布项目的维护记录中，按实际范围填写；不把真实回执或凭据写回本技能。未知字段写明未知及原因，不填看似真实的示例值。

## 本次发布单元

- Skill 名称、源码位置：
- 作者版本、来源提交/ref、仓库内路径：
- 内容范围及许可：
- ZIP/其他材料文件名、根层级、SHA-256：
- 本次意图与已授权平台/账号/可见性：
- 已执行的本地检查及结果：

## 介绍内容计划与执行

按 [内容分层说明](introduction-content.md) 逐项填写。来源需包含文件/ref、源版本或平台实际字段及证据日期；没有对应展示面的项写“不适用”及依据。拟更新全文可以直接放在下方文本块，或引用被发布项目中已准备好的完整文案文件。

## 发布与公开状态

| 平台与确切域名 | owner/namespace/slug | 接收方式与输入范围 | 目标作者版本/平台修订 | 回执或审核链接 | 原始状态/核验时间 | 公开证据与实际内容 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 按本次目标填写 |  | repo/tree/ZIP/CLI/PR 等 |  |  |  |  |  |

每个平台另外分别填写：

- 接收/审核：本次版本的原始状态、回执与时间；未知不能推定待审或通过。
- 版本公开：正确身份的目标版本、公开入口与核验时间。
- 下载包：实际渠道来源、版本/文件/哈希比较及未核验项。
- 简介展示：实际公开短文、语言、与拟更新全文的比较及核验时间。
- 概述展示：实际全文来源/语言/所选版本、功能/系统/依赖/验证范围的比较及核验时间。

每条“成功”应指明证明了哪一步；旧版可见与新版待审可同时存在，版本公开与网页文案更新也分别记录。简介或概述仍旧时明确列为未完成，不以公共 API 版本正确抵消。

## 需要用户手动处理的事项

- 介入原因、当前授权范围及真正缺少的条件：
- 已准备的包/来源记录、简介全文、概述全文及预检结果：
- 当前已核实的页面入口、身份/版本、实际字段与完整操作步骤（包含概述编辑、保存、最终提交和公开核验）：
- 仍待定位的内容来源/编辑能力及具体核对步骤：
- 用户完成后应返回或可只读核对的证据、其余未完成项：

交付时填完可独立准备的实际文案与步骤，不能只写“上传 ZIP、填版本”，也不能让用户自行补概述。入口未确认时不编造操作；沿用会话通知约定提出必要请求并等待实际回复。

把原始日志按需要放在受控位置；摘要省略 Authorization、Cookie、令牌、个人通知地址与无关用户数据。公开发布说明和内部执行日志可以分开保存。
